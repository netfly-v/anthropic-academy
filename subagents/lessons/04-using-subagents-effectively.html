Когда нужны субагенты

Чему научитесь

Видео 4:41 и текст урока

К концу урока вы сможете:

  • отличать задачи, где субагент помогает (исследование кода, ревью, собственный системный промпт), от задач, где он мешает;
  • объяснить, почему «экспертные» субагенты, последовательные конвейеры и субагенты для запуска тестов обычно вредят;
  • решать, делегировать ли задачу, задав себе один вопрос: важна ли промежуточная работа.

Видео и текст урока.

Вы уже умеете создавать субагентов и хорошо их проектировать. Теперь вопрос в другом: когда они действительно помогают, а когда мешают? Разница сводится к одному — важна ли промежуточная работа для вашего главного потока.

Где субагенты сильны

Субагенты лучше всего работают, когда исследование отделено от исполнения. Если каждый шаг задачи зависит от того, что выяснил предыдущий, такую работу стоит вести в главном потоке. Но если вам нужен только ответ, а путь к нему не важен, поручите задачу субагенту.

Субагенты особенно хороши в задачах, где:

  • вам нужен результат, а не пошаговый рассказ о том, как его нашли;
  • исследовательская работа засорила бы контекст главного потока;
  • задаче полезен свежий взгляд или собственный системный промпт.

Исследовательские задачи

Исследование — классический случай для субагента. Допустим, нужно разобраться, как устроена аутентификация в незнакомой кодовой базе. Главному потоку нужно знать, где проверяется JWT, но не нужно видеть каждый файл, который просмотрели по дороге.

Субагент-исследователь может прочитать десятки файлов, проследить цепочки вызовов функций и пройти по разным путям выполнения кода. Всё это исследование остаётся в контексте субагента. Главный поток получает чёткую сводку вроде такой:

JWT validation happens in middleware/auth.js line 42,
called from the Express router in route/api.js

Всю тяжёлую работу сделал субагент. Главный поток получает ровно то, что ему нужно, чтобы двигаться дальше.

Ревью кода

Claude лучше проверяет код, когда тот подан как чужой. Если вы много ходов подряд писали новую функцию в главном потоке, а потом просите этот же поток провести ревью, замечания часто получаются слабыми. Claude сам участвовал в создании кода, поэтому ему трудно посмотреть на него свежим взглядом.

Субагент-рецензент видит изменения в отдельном контексте. Он запускает git diff, читает изменённые файлы и применяет свои специальные критерии ревью, ничего не зная о том, как писался код. Такое разделение к тому же позволяет записать в системный промпт субагента принятые в проекте стандарты ревью, чтобы вся команда проверяла код по одним и тем же критериям.

Собственные системные промпты

Системный промпт Claude Code по умолчанию нацелен на краткие ответы, сосредоточенные на коде. Для программирования это отлично, но подходит не для всего.

Вот два случая, когда собственный системный промпт делает субагента по-настоящему лучше главного потока:

  • Субагент-копирайтер. Дайте ему инструкции о тоне, аудитории и стиле. Промпт Claude Code по умолчанию тяготеет к сжатому техническому стилю, а это совсем не то, что нужно для лендинга или email-рассылки. У субагента-копирайтера могут быть совершенно другие инструкции о манере и структуре текста.
  • Субагент для стилей. Велите ему в системном промпте сначала прочитать файлы вашей дизайн-системы, чтобы ещё до первой строки CSS он знал ваши цветовые переменные, правила отступов и шаблоны компонентов.

Пояснение

  • Explore. Claude Code (на ноябрь 2026) сам поручает широкий поиск по коду встроенному субагенту Explore: он быстрый и работает только на чтение, а глубину поиска задаёт Claude.
  • Ревью и форки. Свежий взгляд даёт обычный субагент: он начинает с чистого контекста. Форк, который Claude может запустить сам (на ноябрь 2026 режим fork включён по умолчанию), наследует весь разговор, поэтому для ревью не подходит.
  • Субагент для стилей и @-упоминания. В видео субагент для стилей @-упоминает файлы дизайн-системы, и, по словам автора, они сами загружаются в контекст при его запуске. Документация (на ноябрь 2026) описывает импорт @path для CLAUDE.md, а для файлов субагентов такого не обещает. Надёжнее вариант из текста урока (велеть сначала прочитать файлы) или поле skills: перечисленные skills целиком попадают в контекст субагента при старте.

Когда субагенты вредят

Накладные расходы на запуск субагента — его работа скрыта от главного потока, а находки сжаты до сводки — оправданы, только когда субагент делает то, чего не может главный поток. Есть три распространённых антипаттерна, которых стоит остерегаться.

Заявленная экспертность

Субагенты, которые заявляют о своей экспертности, помогают редко. Промпты вроде «you are a Python expert» или «you are a Kubernetes specialist» ничего не добавляют: у Claude эти знания уже есть. Так называемый субагент-эксперт не может ничего такого, чего ваш главный поток не сделал бы сам.

Последовательные конвейеры

Последовательные конвейеры из субагентов создают проблемы. Возьмём цепочку из трёх агентов: один воспроизводит баг, второй его отлаживает, третий исправляет. Конвейеры работают, когда задачи действительно независимы. Они ломаются, когда каждый шаг зависит от того, что обнаружил предыдущий, а при исправлении багов так бывает почти всегда. При передаче от агента к агенту информация теряется.

Субагенты для запуска тестов

Субагенты, которые запускают тесты, обычно скрывают нужную вам информацию. Когда тесты падают, для диагностики нужен полный вывод. Субагент, который возвращает «тесты упали», вынуждает писать дополнительные отладочные скрипты, чтобы добыть подробности, которые и так были бы видны при прямом запуске. В испытаниях схема с субагентом для запуска тестов показала худший результат из всех конфигураций.

Пояснение

Документация Claude Code (на ноябрь 2026), наоборот, называет прогон тестов одним из самых удачных применений субагента: многословный вывод остаётся в его контексте, а в главный поток приходит выжимка, например по промпту «Use a subagent to run the test suite and report only the failing tests with their error messages». Вредит лишь субагент, который отвечает одним «тесты упали». Если же вы исправляете код, глядя на полный вывод, и реагируете на каждый запуск, прогоняйте тесты в главном потоке.

Правило выбора

Решая, нужен ли субагент, задайте себе один вопрос: важна ли промежуточная работа?

Если ответ «нет» — вам нужен только итоговый результат, — поручите задачу субагенту. Если ответ «да» — вам нужно видеть, что происходит по ходу дела, и реагировать на это, — оставьте работу в главном потоке.

Используйте субагентов для:

  • исследования и изучения кода;
  • ревью кода;
  • задач, которым нужен собственный системный промпт.

Не используйте субагентов для:

  • «экспертных» ролей, которые не добавляют реальных возможностей;
  • многошаговых конвейеров, где каждый шаг зависит от предыдущего;
  • запуска тестов, когда для отладки нужен полный вывод.
