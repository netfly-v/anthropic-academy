Ревью кода

Чему научитесь

Текстовый урок, около 10 минут

К концу урока вы сможете:

  • читать diff командой /diff и находить то, о чём сводка Claude умолчала: непрошеные правки, ослабленные тесты, новые пакеты и значения, зашитые в код;
  • откатывать неудачное изменение через /rewind;
  • получать второе мнение из чистого контекста командой /code-review;
  • раскладывать находки ревью по стопкам «исправить сейчас», «спросить почему» и «оставить» и просить доказательства к каждому исправлению.

Когда вы даёте Claude Code задачу в своей кодовой базе, Claude часто отчитывается коротко. Но за описанием того, что Claude изменил, может стоять целый набор изменённых файлов — от мелких правок до крупных переделок. Сессия, которая сама написала эти изменения (и сама их объяснила), зачастую не лучший их судья. Хорошая привычка — самому просматривать каждое изменение, прежде чем его оставить, а потом просить Claude проверить его ещё раз из чистого контекста, без истории этой сессии.

Смотрите на сами изменения

Diff — это изменение в виде «до и после»: удалённые и добавленные строки, файл за файлом. Команда /diff открывает интерактивный просмотр ваших незакоммиченных изменений в таком виде, а ещё может показать, что изменил каждый ход Claude. Стрелками вверх и вниз переходите между файлами, клавишей Enter открывайте файл.

/diff

В /diff ничего не видно? /diff и /code-review узнают об изменениях из записей git, поэтому проект должен лежать в git-репозитории. Git — инструмент контроля версий, которым уже пользуется большинство проектов, и на нём держится шаг Commit из урока «Цикл Explore → Plan → Code → Commit». Сам git в этом курсе не объясняется. Если ваш проект ещё не в git, попросите Claude настроить репозиторий и сделать первый коммит до следующей задачи. С этого момента любое изменение будет видно в обеих командах. А о ревью изменения, которое перед вами сейчас, попросите обычными словами (как — ниже). Если вы работаете с другой системой контроля версий, /diff и /code-review ваших изменений не увидят, но всё остальное по-прежнему применимо: читайте изменение в своём инструменте, обычными словами просите Claude проверить файлы, которые он трогал, а /rewind всё равно работает, потому что Claude сам отслеживает свои правки.

В первую очередь второго взгляда всегда заслуживают:

  • Изменения, о которых вы не просили. Значение в конфиге, которое поменялось, пока Claude работал с этим файлом, или переписанный вспомогательный метод, о котором вы не упоминали.
  • Тесты, которые стали слабее. Если в проекте, с которым вы работаете, есть тесты, найдите те, что пропустили, удалили или ослабляли, пока они не стали проходить.
  • Новые пакеты и значения, зашитые в код. Зависимость, добавленная ради одной-единственной функции, или URL либо ключ, вписанный прямо в код.

Если неверно всё изменение целиком, выполните /rewind (или дважды нажмите Esc при пустой строке ввода), укажите промпт, который к нему привёл, и выберите пункт Restore code and conversation. Одно ограничение, о котором стоит знать: файлы, которые изменили запущенные Claude shell-команды (например, установка пакета), не откатываются.

Пояснение

  • Как выглядит /diff. Стрелки и Enter из урока — это классический интерфейс. В полноэкранном режиме отрисовки (на ноябрь 2026 — по умолчанию у многих новых пользователей) /diff открывает панель рядом с разговором, файл в ней выбирают щелчком.
  • Что откатывает /rewind. Урок упрощает: не откатывается файл, который меняли только shell-команды (например, при установке пакета). Если Claude уже правил файл своими инструментами, /rewind отменит и более поздние изменения shell-команд в нём.

В упражнении ниже — небольшая задача с формой регистрации: сверху сводка Claude, под ней восемь файлов, которые Claude затронул.

Упражнение. Прочитайте сводку Claude о выполненной задаче, раскройте diff каждого изменённого файла и отметьте те, что заслуживают второго взгляда; после каждой попытки вы получаете отзыв. Цель — убедиться, что даже правдивая сводка может умалчивать об изменениях, которые стоит проверить.

Сравните сводку Claude с diff

Claude выполнил задачу и прислал сводку. Всё в ней правда. Теперь сравните её с файлами, которые изменились.

  1. Прочитайте сводку Claude.
  2. Раскройте diff каждого файла и посмотрите, что в нём изменилось.
  3. Отметьте три файла, которые, скорее всего, заслуживают второго взгляда.

Сводка Claude. Промпт: добавить в форму регистрации проверку ввода — проверять формат email и требовать пароль не короче 8 символов, с сообщениями об ошибках прямо у полей. Ответ Claude: проверка ввода в форму регистрации добавлена; формат email и длина пароля проверяются до отправки; сообщения об ошибках появляются под каждым полем; все тесты проходят.

Попросите второе мнение

В уроке «Цикл Explore → Plan → Code → Commit» говорилось, что перед коммитом изменение должен посмотреть второй рецензент. Длинная сессия тянет за собой всё, что успела прочитать и решить. Это тот самый контекст, которым вы учились управлять в предыдущем уроке, и именно такая история рецензенту не нужна. /code-review и есть этот второй рецензент: он проверяет изменение в чистом контексте, без всякой истории вашей сессии, и сообщает, что нашёл. Он ничего не правит, пока вы об этом не попросите.

/code-review

Ревью идёт в фоне — от нескольких секунд до нескольких минут — и расходует ваш лимит использования, как любая другая задача, так что приберегайте его для изменений, которые заслуживают второго взгляда. Когда ревью закончится, находки появятся в вашем разговоре. Можно попросить и обычными словами: Claude может запустить то же ревью по вашей просьбе. Если вместо запуска ревью Claude отвечает прямо в разговоре, выполните команду сами.

Review the changes you just made. Report problems; don't fix anything yet.

Нужно ревью полегче или поглубже? Добавьте к команде уровень effort. /code-review low сообщает только о находках, в которых больше всего уверен, поэтому ложных тревог будет меньше. /code-review high охватывает больше и может включить находки, в которых уверен меньше. Введённый уровень запоминается для следующих ревью, пока вы не введёте другой.

Пояснение

  • Что проверяет /code-review. На ноябрь 2026 это встроенный skill: в терминале он работает как фоновый субагент с собственным контекстным окном и историю вашей сессии не видит. Без аргументов он смотрит коммиты текущей ветки, которых ещё нет в upstream, вместе с незакоммиченными изменениями. Синоним команды — /review.
  • Уровни и исправления. Кроме low и high есть medium, xhigh и max; пока уровень ни разу не вводили, берётся текущий effort сессии. Флаг --fix просит сразу применить находки, но фоновое ревью вносит их в обход контрольных точек: файлы, которые Claude в разговоре сам не правил, /rewind не вернёт — поможет git.

По изменению формы регистрации ревью выдало четыре находки.

Ниже — что сообщил /code-review по учебному изменению: у каждой находки есть место в файле, метка correctness или style и описание в одну строку. Вот что замечает рецензент, который смотрит на изменение из чистого контекста; дальше вы разложите эти находки по стопкам.

> /code-review

Reviewed 8 changed files. 4 findings:

1. src/components/SignupForm.test.tsx:18 [correctness]
   A test was skipped and an assertion weakened; a form that submits empty values would still pass.
2. src/lib/validate.ts:4 [correctness]
   isValidEmail doesn't trim leading or trailing spaces, so an address pasted with a stray space is rejected.
3. src/config.ts:1 [correctness]
   API_URL is hard-coded to localhost:3000; a production build would send signups to a development address.
4. src/styles/form.css:1 [style]
   Error text uses a hex color instead of the project's --color-danger variable.

Решите, что делать с каждой находкой

Отнесите каждую находку к одной из трёх стопок:

  1. Исправить сейчас (Fix now). Это настоящая проблема, она важна, и её нужно исправить.
  2. Спросить почему (Ask why). Сюда попадают находки, которые вы не можете толком проверить или которые кажутся странными. Рецензент, который читает изменения с чистого листа, тоже может что-то упустить.
  3. Оставить (Leave it). Проблема настоящая, но мелкая или несущественная. Такие находки часто можно собрать в общий пакет исправлений и закрыть разом в одной из следующих сессий.

Чтобы «спросить почему», процитируйте Claude его находку и попросите проверить ещё раз. О второй находке выше вы написали бы так:

You reported that isValidEmail doesn't trim spaces, but line 4 calls trim(). Check again and tell me whether the finding stands.

Когда просите что-то исправить, полезно сразу просить и доказательства:

Fix the first finding: don't skip the empty-email test and restore the original assertion. Then run the tests and show me the output.

Если исправление в итоге разрастётся в большое самостоятельное изменение, запустите ревью ещё раз.

Когда стоит проверять внимательнее

Простому изменению в одну строку часто хватает беглого взгляда на diff — и больше ничего не нужно. Ревью и от человека, и от Claude нужно, когда изменение больше, чем вы способны удержать в голове, когда оно затрагивает что-то чувствительное или делает что-то разрушительное, а также перед тем, как передать работу коллеге.

Это то же самое, что Claude Code Review? Нет. Claude Code Review — отдельный продукт для команд: владелец (Owner) вашей организации в Claude включает его для репозитория на GitHub, и продукт публикует свои находки в pull requests. Для этого урока он не нужен.

Попробуйте: разложите четыре находки

Упражнение. Отнесите каждую находку инструмента ревью кода к одной из стопок — «исправить сейчас», «спросить почему» или «оставить»; после каждого выбора открывается отзыв. Упражнение показывает, что не каждая находка требует немедленного исправления, а рецензент иногда ошибается.

В какую стопку отправить каждую из этих находок?

1. src/components/SignupForm.test.tsx:18 · correctness. Тест пропустили, а проверку ослабили: форма, которая отправляет пустые значения, всё равно пройдёт тест.

- it("blocks submit when the email is empty", async () => {
+ it.skip("blocks submit when the email is empty", async () => {
  …
-   expect(onSubmit).toHaveBeenCalledWith({ email: "sam@example.com", password: "correct-horse-battery" });
+   expect(onSubmit).toHaveBeenCalled();

2. src/lib/validate.ts:4 · correctness. isValidEmail не обрезает пробелы в начале и в конце, поэтому адрес, вставленный с лишним пробелом, отклоняется.

3  export function isValidEmail(value: string) {
4    return isEmail(value.trim());
5  }

3. src/config.ts:1 · correctness. API_URL жёстко задан как localhost:3000: продакшен-сборка будет отправлять регистрации на адрес для разработки.

- export const API_URL = import.meta.env.VITE_API_URL;
+ export const API_URL = "http://localhost:3000"; // local testing

4. src/styles/form.css:1 · style. Для текста ошибки задан цвет в hex вместо переменной проекта --color-danger.

1  .field-error { color: #c0392b; font-size: 0.875rem; margin-top: 4px; }

Пояснение

На Academy после каждого выбора появляется отзыв, в конспекте его нет. По критериям урока первая и третья находки — «исправить сейчас» (ослабленный тест; продакшен-сборка отправит регистрации на адрес для разработки); вторая — «спросить почему»: trim() в строке 4 уже вызывается, и рецензент, похоже, ошибся; четвёртая — «оставить»: проблема настоящая, но мелкая.

Итог

  • Прежде чем доверять одной только сводке, прочитайте сам diff изменённых файлов. Выполните /diff и ищите изменения, о которых вы не просили, ослабленные тесты, новые пакеты и значения, зашитые в код.
  • Получите второе мнение из чистого контекста командой /code-review (или попросите обычными словами, и Claude сам запустит ревью). Рецензент только сообщает о находках, а Claude ничего не правит, пока вы не попросите.
  • Относите каждую находку к одной из стопок — «исправить сейчас», «спросить почему» или «оставить» — и к каждой просьбе об исправлении добавляйте просьбу показать доказательства.

Если рецензент несколько раз отмечает одну и ту же проблему, возможно, стоит записать правило, которое Claude будет читать в начале каждой сессии. Для этого есть файл CLAUDE.md — о нём следующий урок.
