Skills для проверки

Чему научитесь

Видео 1:48 и текст урока

К концу урока вы сможете:

  • объяснить, почему первым стоит сделать skill, который проверяет работу, и из каких шагов он состоит;
  • держать главный файл skill коротким, а подробную справку и скрипты выносить в соседние файлы;
  • решать, куда положить правило: в CLAUDE.md, в skill или в hook.

Видео и текст урока.

Когда проект растёт, вы начинаете замечать, что одна и та же работа повторяется снова и снова. Вы уже знаете, что skills — хороший способ автоматизировать повторяющуюся работу. В этом уроке разберём одну конкретную задачу, с которой skills справляются особенно хорошо: проверку собственной работы. Если делать какой-то skill первым, то именно этот.

Почему начинать стоит со skill для проверки

Вспомните, как вы обычно проверяете работу Claude. Вы просите его что-нибудь отрефакторить, он заканчивает, и дальше вам надо не забыть всё перепроверить. Может быть, вы попросите его прогнать тесты. Может быть, сами прочитаете diff. Беда в том, что проверка зависит от того, не забудете ли вы попросить о ней. Пропустите этот шаг один раз — и плохой код проскочит.

Skill для проверки убирает эту зависимость. Вот как он устроен. Вы просите Claude что-нибудь отрефакторить. Когда он заканчивает, изменение подходит под описание skill, поэтому skill срабатывает сам. Дальше он:

  • прогоняет набор тестов;
  • читает diff;
  • проверяет, что ни один тест не ослабили только ради того, чтобы всё прошло;
  • сообщает, пройдена проверка или нет, и прикладывает доказательства.

Всё это происходит без вашей просьбы. Запускает skill его описание, а запустившись, он каждый раз проходит одни и те же шаги.

Обратите внимание на последнюю проверку в этой цепочке. Мало прогнать тесты и увидеть зелёный результат. Тест можно незаметно ослабить так, что он будет проходить при любом коде. Поэтому skill читает diff и убеждается, что тесты не ослабили. «Готово» не значит «по diff код выглядит правильно». «Готово» — это когда обязательные проверки запущены, их результат действительно увиден, а итог прямо назван в отчёте.

Та же схема подходит для любой процедуры, которую повторяет ваша команда: чеклист релиза, рецепт миграции, проверка перед pull request. Простое правило: если вы дважды набрали одну и ту же многошаговую инструкцию, это уже skill.

Пояснение

«Срабатывает сам» — не гарантия: Claude сравнивает задачу с описаниями skills и сам решает, загрузить ли подходящий. По документации Claude Code (на ноябрь 2026), описание должно объяснять и что делает skill, и когда его использовать, причём главный случай лучше ставить в начало. Если skill не сработал, его можно вызвать вручную командой /имя-skill. Гарантию даёт только hook — см. раздел «Куда класть какое правило».

В папке skill может лежать не только инструкция

Skill — это не только один файл skill.md. Рядом с ним в папке может лежать и другое, и именно это делает skills таким сильным средством проверки.

  • Положите рядом со skill файл reference.md с подробным материалом и сошлитесь на него из skill.md. Claude прочитает его, только когда ему действительно понадобятся эти подробности. Главный файл при этом остаётся коротким.
  • Скрипты тоже кладите в эту папку. Claude их выполняет, а не загружает их содержимое в контекст. Значит, у skill могут быть собственные инструменты — например, check.sh, который прогоняет все проверки.

Вывод: сам skill.md держите компактным. Объёмный материал — длинные объяснения и исполняемые скрипты — выносите в соседние файлы. Компактный файл описывает, что делать, а в соседних лежат подробности и инструменты.

Пояснение

  • Имя файла. В уроке файл назван skill.md, но в документации Claude Code и в спецификации Agent Skills главный файл называется SKILL.md, заглавными буквами, и лежит в собственной папке skill: .claude/skills/<имя>/SKILL.md.
  • Соседние файлы. В SKILL.md стоит написать, что лежит в каждом таком файле и когда его открывать. Код скрипта в контекст не попадает, туда приходит только его вывод: например, «тесты прошли» или текст ошибки.

Куда класть какое правило

У вас уже есть три места для инструкций, и их легко перепутать. Вот быстрый способ их различать.

Соглашения, которые действуют всё время, например правила именования или то, куда класть файлы, пишут в файл CLAUDE.md. Процедуры и справочный материал для определённого вида задач кладут в skill.

Есть и третий случай. Правило, которое Claude не должен иметь возможности пропустить, кладут в hook, а не в CLAUDE.md и не в skill. Дело в том, что CLAUDE.md и skills — это инструкции, которым Claude следует, а hook — это код, который действительно выполняется. Если пропустить правило нельзя, не полагайтесь только на инструкции.

Итог

Skill — это папка с файлом skill.md внутри: имя, описание, которое запускает skill, и сама процедура. Пока skill на самом деле не понадобился, в контекст загружаются только описания, поэтому упаковать в skill каждую повторяющуюся процедуру ничего не стоит.

Начните с проверки. Сделайте skill, закоммитьте его в .claude/skills вашего проекта — и тот же приём получит вся команда. Работу каждого будут проверять одинаково, автоматически, и никому не придётся помнить, что об этом надо попросить.

Пояснение

«Ничего не стоит» — почти. Описание каждого skill занимает контекст на каждом ходе, вызывается skill или нет. В Claude Code (на ноябрь 2026) список skills по умолчанию ограничен бюджетом: если skills слишком много, описания тех, что вызываются реже всего, убираются (имена остаются), и Claude теряет ключевые слова, по которым сопоставляет с ними задачу. Поэтому описание пишите коротким, с главным случаем в начале, а лишние skills отключайте.
