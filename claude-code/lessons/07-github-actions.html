GitHub Actions и Code Review

Чему научитесь

Видео 3:16 и текст урока

К концу урока вы сможете:

  • отличить управляемый сервис Code Review от GitHub Action и выбрать подходящий для задачи;
  • объяснить, как Code Review включают, когда он запускается и чего он не делает;
  • подключить anthropics/claude-code-action@v1 через /install-github-app и разобраться в его входных параметрах;
  • ограничить запуск без присмотра через claude_args: лимит ходов, режим разрешений, разрешённые инструменты.

Видео и текст урока.

Лучшее место, чтобы передать Claude повторяющуюся работу, — pull request. Здесь проходит ревью, сюда попадают изменения, и здесь же живёт немалая часть вашей рутины. Поставить Claude на эту работу можно двумя способами, и они решают разные задачи. Первый — управляемый сервис, который достаточно включить. Второй — GitHub Action, который вы подключаете сами. Разберём оба и поймём, когда какой из них выбирать.

Управляемый путь: Code Review

Самый простой вариант — Code Review. Это сервис, размещённый у Anthropic: он проверяет ваши pull request через GitHub-приложение Claude (Claude GitHub App). Вам ничего не нужно ни собирать, ни где-то размещать. Вы включаете его — и он начинает оставлять замечания в комментариях прямо к тем строкам, где это важно.

Включает его администратор организации — в настройках администратора Claude Code. Там есть раздел Code review с кнопкой Configure, которая подключает сервис к вашим репозиториям.

Дальше администратор устанавливает GitHub-приложение Claude, выбирает, за какими репозиториями оно следит, и решает, когда запускать ревью. Вариантов запуска несколько:

  • один раз, когда PR открывают;
  • при каждом push в PR;
  • только когда кто-то напишет в комментарии @claude review.

Когда сервис включён, всё работает на инфраструктуре Anthropic. Группа агентов-ревьюеров анализирует diff с учётом всей кодовой базы, а не изменённые строки в отрыве от остального кода. Затем сервис публикует замечания в комментариях к конкретным строкам, с пометкой серьёзности, а в check run — сводную таблицу.

Вот как выглядит одно такое замечание. Оно приходит от Claude комментарием прямо к строке — с понятным объяснением и предложенным исправлением.

Удобно, что сервис убирает дубли и ранжирует замечания. Поэтому вместо вороха придирок вы видите несколько настоящих проблем, которые стоят вашего внимания.

Что Code Review делает, а чего нет

Несколько вещей, которые стоит помнить о границах сервиса:

  • Он никогда не одобряет и не блокирует PR. Последнее слово за человеком: Claude отмечает проблемы, решаете вы.
  • Управляемого автоисправления нет. Сервис только публикует замечания.
  • Сейчас это research preview, доступный на планах Team и Enterprise, так что поведение ещё будет меняться.

Раз автоисправления в сервисе нет, исправлять найденное приходится локально. В вашем терминале команда /code-review проверяет diff, а её флаг --fix применяет найденное к рабочему дереву. Порядок работы такой: Claude находит проблему в PR, вы забираете ветку к себе и исправляете локально.

Пояснение

  • Статус и включение. На ноябрь 2026 документация уже не называет Code Review research preview: это сервис для планов Team и Enterprise. Включает его Owner организации переключателем Allow code review (claude.ai → Admin settings → Claude Code); кнопки Configure, о которой говорит урок, в текущей инструкции нет.
  • /code-review — отдельное ревью. Это собственная проверка изменений в вашей сессии, а не замечания сервиса: --fix применяет к рабочему дереву то, что нашёл этот прогон.

Путь «своими руками»: GitHub Action

Code Review берёт на себя ревью. Когда задача шире ревью, берите GitHub Action. Он нужен для вашего собственного CI: вносить изменения по комментарию, запускать отчёты по расписанию — всё, для чего вы обычно пишете workflow. Action запускает агента по комментариям в PR, по расписанию и по любому событию GitHub.

Настройка начинается в Claude Code. Выполните команду /install-github-app. Для этого нужны права администратора репозитория. Slash-команда проведёт вас через установку GitHub-приложения и создание в репозитории секрета с ключом Anthropic API.

Сам action — anthropics/claude-code-action@v1. Вот входные параметры, которые вы действительно будете использовать:

  • anthropic_api_key — необязательный.
  • github_token — по умолчанию secrets.GITHUB_TOKEN.
  • trigger_phrase — что action ищет в комментариях. По умолчанию @claude.
  • use_bedrock / use_vertex — переключение на этих провайдеров, если вы работаете через Bedrock или Vertex.
  • prompt — инструкция для запуска.
  • claude_args — строка аргументов CLI, которая передаётся прямо в Claude Code.

Workflow, который откликается на @claude

Положите workflow в .github/workflows/claude.yaml — и он будет ловить @claude в комментариях к PR и к issue. Главный шаг выглядит так:

- uses: anthropics/claude-code-action@v1
  with:
    anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
    github_token: ${{ secrets.GITHUB_TOKEN }}
    trigger_phrase: "@claude"
    prompt: "Your instructions here"
    claude_args: "--max-turns 5 --model claude-sonnet-5"

Теперь кто-то пишет в pull request @claude implement the spec in the linked Linear issue — и action подхватывает запрос. Claude пушит коммиты и оставляет комментарии о том, что сделал.

Пояснение

  • prompt переключает режим. Без prompt action работает в режиме interactive: ждёт фразу-триггер и отвечает комментарием. С prompt, как в примере урока, — automation: выполняет инструкцию при любом событии, запустившем workflow, не дожидаясь упоминания, а результат по умолчанию пишет в лог запуска. Поэтому workflow для ответов на @claude в документации написан без prompt.
  • github_token. Документация на ноябрь 2026 расходится с уроком: если параметр не задан, action авторизуется как Claude GitHub App. Если передать ${{ secrets.GITHUB_TOKEN }}, как в примере, CI по коммитам Claude не запустится.
  • anthropic_api_key. В тексте урока он необязательный, в видео — обязательный. Ключ нужен для работы напрямую с Claude API, если вы не используете claude_code_oauth_token (подписка) или workload identity federation; с Bedrock и Vertex он не используется.
  • Модель. claude-sonnet-5 на ноябрь 2026 — legacy-модель; текущий Sonnet — claude-sonnet-5-5.

Workflow по расписанию

Тот же action подходит для ежедневной сводки. Cron-триггер срабатывает, скажем, в 9:00 UTC, action запускается, Claude публикует результаты. Можно добавить и триггер workflow_dispatch, чтобы запускать workflow вручную со вкладки Actions.

Пока action работает, на вкладке Actions можно следить, как он проходит шаги, — как и у любого другого workflow GitHub.

Тонкая настройка через claude_args

Строка claude_args — место для тонкой настройки. Несколько рычагов, которые стоит знать:

  • --max-turns 5 жёстко ограничивает цикл агента, чтобы он не крутился бесконечно.
  • Режим разрешений. Job без присмотра не должен останавливаться с вопросами: отвечать на них некому.
  • Разрешённые инструменты. Дайте job ровно то, что ему нужно, и ничего сверх. Для отчёта это значит: только чтение.

Пояснение

  • Какие это флаги. В тексте урока они не названы; в видео режим разрешений — --permission-mode dontAsk: каждый запрос разрешения превращается в отказ, и сессия никогда не ждёт ввода. Разрешённые инструменты задаёт --allowedTools; для CI документация рекомендует именно эту пару.
  • Инструменты сами не выдаются. Если prompt — обычный текст, у Claude нет доступа ни к shell, ни к GitHub API, пока вы не разрешите нужное, например через --allowedTools.

Что выбрать?

Коротко:

  • Для ревью PR — управляемый путь. Включите Code Review, пусть GitHub-приложение публикует замечания к строкам, а исправления применяйте локально через /code-review --fix.
  • Берите action, когда задача шире ревью: /install-github-app для настройки, один workflow для упоминаний @claude, ещё один — для cron, а вся тонкая настройка — в claude_args.

Начните с управляемого сервиса. Переходите на action, как только вам понадобится, чтобы Claude действительно что-то делал в CI, а не только комментировал.
