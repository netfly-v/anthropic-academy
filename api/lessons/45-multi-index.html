Смотреть урок на Skilljar A Multi-Index RAG pipeline · 6:45

Мы сделали отдельные реализации семантического поиска (на векторных эмбеддингах) и лексического (на BM25). Пора объединить их в единый конвейер поиска, который использует сильные стороны обоих подходов.

Многоиндексная архитектура

У классов VectorIndex и BM25Index почти одинаковый API: у обоих есть методы add_document() и search(). Благодаря этому их легко обернуть в новый класс Retriever.

Retriever — координатор: он передаёт запрос пользователя в оба индекса, собирает их результаты и объединяет методом reciprocal rank fusion (RRF).

Что такое reciprocal rank fusion

Объединить результаты разных методов поиска — не то же самое, что склеить списки. У каждого метода своя система оценок, поэтому нужен способ привести их рейтинги к общему знаменателю и честно объединить.

Разберём RRF на примере. Допустим, ищем информацию об «INC-2023-Q4-011» и получаем:

  • VectorIndex: Section 2 (ранг 1), Section 7 (ранг 2), Section 6 (ранг 3);
  • BM25Index: Section 6 (ранг 1), Section 2 (ранг 2), Section 7 (ранг 3).

Сводим их в одну таблицу с рангами каждого фрагмента в обоих индексах и применяем формулу RRF:

RRF_score(d) = Σ(1 / (k + rank_i(d)))

Здесь k — константа (часто 60, но мы возьмём 1, чтобы результаты были нагляднее), а rank_i(d) — ранг документа d в i-м рейтинге.

Для нашего примера:

  • Section 2: 1.0/(1+1) + 1.0/(1+2) = 0.833;
  • Section 7: 1.0/(1+2) + 1.0/(1+3) = 0.583;
  • Section 6: 1.0/(1+3) + 1.0/(1+1) = 0.75.

Итоговый рейтинг: Section 2 (0.833), Section 6 (0.75), Section 7 (0.583). Это интуитивно понятно: Section 2 хорошо показал себя в обоих индексах, поэтому поднимается наверх.

Пояснение

search в уроке — набросок, а не рабочий код: список all_results так и остаётся пустым. Полная логика выглядит примерно так:

    def search(self, query_text: str, k: int = 1, k_rrf: int = 60):
        all_results = [index.search(query_text, k * 5) for index in self._indexes]

        scores, docs = {}, {}
        for results in all_results:
            for rank, (doc, _) in enumerate(results, start=1):
                key = id(doc)  # или стабильный id документа
                docs[key] = doc
                scores[key] = scores.get(key, 0) + 1 / (k_rrf + rank)

        best = sorted(scores, key=scores.get, reverse=True)[:k]
        return [(docs[key], scores[key]) for key in best]

Для неё нужны from typing import Any, Dict и протокол SearchIndex из ноутбука курса. Обратите внимание: из каждого индекса берут больше кандидатов, чем k, — иначе документ, хороший в одном индексе и средний в другом, может не попасть в слияние.

Проверяем гибридный подход

Помните прошлую проблему: поиск «what happened with INC-2023-Q4-011?» только по векторам давал неожиданные результаты. Инцидент по кибербезопасности (Section 10) шёл первым, но вторым оказывался финансовый анализ (Section 3) вместо более подходящего раздела о разработке ПО.

С гибридным Retriever результаты гораздо лучше:

  • Section 10: Cybersecurity Analysis — Incident Response Report (самый подходящий);
  • Section 2: Software Engineering — Project Phoenix Stability Enhancements (второй);
  • Section 5: Legal Developments (третий).

Это показывает, как сочетание семантического и лексического поиска преодолевает ограничения каждого подхода в отдельности.

Расширяемость

Красота этой архитектуры — в расширяемости. Поскольку все индексы реализуют один протокол SearchIndex с методами add_document() и search(), можно легко добавлять новые методы поиска:

Нужен индекс по ключевым словам? Поиск по графу? Специализированный индекс для предметной области? Достаточно реализовать тот же интерфейс, и Retriever автоматически включит его в слияние.

Модульный подход сохраняет каждую реализацию поиска сфокусированной и тестируемой и даёт чистый способ объединить их сильные стороны в итоговой системе.

Пояснение

  • Почему RRF, а не сумма оценок. Оценки векторного поиска и BM25 в разных шкалах, складывать их напрямую бессмысленно. RRF использует только места в рейтингах, поэтому шкалы не важны. Большое k (60) сглаживает разницу между первыми местами, маленькое (1, как в примере) сильнее награждает лидеров.
  • Следующий шаг — Contextual Retrieval. В статье Anthropic о contextual retrieval к каждому фрагменту перед индексацией Claude дописывает короткий контекст из всего документа («это раздел о… из отчёта компании X за квартал Y»), и по нему строят и эмбеддинги, и BM25. По данным статьи, это сократило долю неудачных поисков (нужный фрагмент не в первых 20) на 49%, а с реранкингом — на 67%. Генерация контекста дешёвая благодаря prompt caching — о нём в следующем блоке.
  • Реранкинг. Ещё одно популярное улучшение — после слияния пропустить кандидатов через модель-реранкер (например, rerank-3 от Voyage), которая точнее оценивает релевантность пары «вопрос — фрагмент».
