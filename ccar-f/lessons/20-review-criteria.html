Явные критерии ревью вместо «будь осторожен»

Домен 4 · подпункты 4.1, 4.2, 4.4

Что уже есть в курсах

  • API · Конкретика — явные указания подняли оценку промпта более чем вдвое.
  • API · Упражнение: критерии для грейдера — критерии хорошего решения прямо в промпте проверяющей модели.
  • API · Примеры в промпте — примеры на пограничные случаи и пояснение, чем пример хорош.
  • API · Изображения — шкала риска от 1 до 4, у каждого уровня свой конкретный признак.
  • Claude Code · CLAUDE.md, которому следуют — правило, которое можно проверить, работает, а «следуй лучшим практикам» — нет.
  • Claude Code 101 · Ревью кода — /code-review и его уровни effort, разбор находок на «исправить», «спросить почему», «оставить».
  • Claude Code · GitHub Actions и Code Review — сервис ревью убирает дубли и ставит находкам пометку серьёзности.

Простыми словами

Автоматическое ревью полезно, пока разработчики читают его находки. Каждое ложное срабатывание приучает их пролистывать комментарии бота, поэтому для доверия важна точность (precision): доля находок, оказавшихся настоящими проблемами.

Почему «будь осторожен» не помогает. «Будь осторожнее» или «пиши, только если уверен» не называют, что в вашей команде считается шумом, а уверена модель бывает и в придирке к имени переменной. Opus 4.8 и Opus 5, по документации на ноябрь 2026, исполняют такую фразу буквально: находят ошибку, но молчат, если она ниже планки, — и пропадают настоящие проблемы. Точность дают явные категории:

  • сообщать: ошибки логики, уязвимости, утечки данных и секретов;
  • пропускать: стиль и имена, сгенерированные файлы, принятые в модуле приёмы и всё, что и так ловят линтер и CI.

Шум не остаётся в своей категории. После десятка ложных «возможных гонок» разработчик закрывает не читая и точные замечания об уязвимостях. Поэтому шумную категорию временно отключают, точные оставляют, а для выключенной тем временем переписывают критерии и примеры.

Уровни серьёзности с образцами. Без определений одна и та же проблема в одном прогоне «важная», в другом — «мелочь». У каждого уровня — определение и образец из вашего кода:

  • критично — SQL-запрос склеен из строки, пришедшей от пользователя;
  • важно — ошибка списания денег перехвачена и нигде не записана;
  • мелочь — проверка на пустое значение повторена дважды.

Пары «допустимо / проблема». Против ложных срабатываний примеры (few-shot) составляют парами похожих фрагментов: пустой обработчик исключения с комментарием «отмену пользователем игнорируем» допустим, а пустой обработчик вокруг списания денег — проблема. К паре добавляют пояснение: по нему Claude обобщает правило на похожие случаи (см. «Few-shot»).

Метка шаблона для разбора отказов. В схему находки добавляют поле detected_pattern — короткую метку того, на что отреагировал ревьюер: «пустой catch», «SQL из строки». Отклонённые находки сохраняют с меткой, и сводка показывает, какие шаблоны дают больше всего отказов: критерии правят для них. Без метки видно только, что отказов много.

Пример

Платёжный сервис ревьюит pull request в CI: Claude Code в неинтерактивном режиме отдаёт находки в JSON по схеме (флаг --json-schema). В промпте — «Be careful and flag only issues you are sure about». Через месяц разработчики отклоняли почти половину находок, в основном «возможные гонки» в обработчиках очереди, где порядок и так гарантирован. Комментарии бота стали закрывать не читая — и пропустили запись номера карты в журнал.

Что делает архитектор:

  1. Заменяет эту фразу списком «сообщать / пропускать».
  2. Выключает категорию «конкурентность» и пишет для неё пары: очередь с гарантированным порядком — допустимо, общий счётчик без блокировки — проблема.
  3. Задаёт три уровня серьёзности с примерами из кода сервиса.
  4. Делает detected_pattern обязательным полем схемы и раз в неделю смотрит, какие шаблоны отклоняют чаще всего.
  5. Включает конкурентность снова, когда на прошлых pull request она больше не шумит.

Как это спрашивают

Типичная ситуация: разработчики не доверяют ревью из-за ложных срабатываний или одна проблема получает разную серьёзность в разных прогонах. Неверные ходы:

  • «Будь осторожнее» или порог по оценке уверенности от самой модели. Граница шума не названа, а самооценка не знает норм команды.
  • Модель побольше. Ваших норм не знает и она.
  • Выключить ревью целиком. Пропадут и точные категории.
  • Чинить промпт, не выключая шумную категорию. Пока идёт настройка, люди отвыкают читать бота.
  • Уровни серьёзности без примеров. Оценки останутся разными.
  • Перечитывать отказы вручную. Без метки шаблона не видно, что даёт шум.

Курс vs экзамен

На экзамене фильтр по уверенности — неверный ответ, хотя продукт на ноябрь 2026 им пользуется: /code-review low показывает только самые уверенные находки, а руководства по Opus 4.8 и Opus 5 советуют сообщать обо всём, указывая уверенность и серьёзность, и отсеивать отдельным шагом (в одном проходе — называть порог конкретно). На экзамене выбирайте явные категории.

Документация

  • Prompting best practices: Be clear and direct — Claude как толковый новый сотрудник, который не знает ваших норм; чем конкретнее указания, тем лучше результат.
  • Prompting best practices: Add context to improve performance — причина правила помогает: Claude обобщает по объяснению.
  • Prompting best practices: Use examples effectively — 3–5 релевантных и разнообразных примеров в тегах <example>.
  • Prompting Claude Opus 4.8: Code review harnesses — «be conservative» и «only report high-severity issues» модель исполняет буквально и сообщает меньше; совет: на шаге поиска сообщать обо всём, указывая уверенность и серьёзность, а в одном проходе называть порог конкретно.
  • Prompting Claude Opus 5: Capability improvements — то же для Opus 5: на «be conservative» модель сообщает меньше; просить сообщать обо всём и отсеивать отдельным проходом.
  • Customize Code Review — REVIEW.md: что значит Important, что не сообщать, что проверять всегда, лимит мелких замечаний, доказательства для класса находок.
  • Read and request reviews on a pull request — уровни Important, Nit и Pre-existing; как отклонить находку; повторяющуюся находку закрывают правилом в REVIEW.md.
  • Code Review — по умолчанию ищет ошибки корректности, а не форматирование; шаг проверки отсеивает ложные срабатывания.
  • Review locally with /code-review — уровень effort low: только самые уверенные находки и меньше ложных срабатываний; ревью следует CLAUDE.md.
  • Claude Code GitHub Actions — ревью pull request в своём CI; критерии ревью и правила проекта — в CLAUDE.md.
  • Run Claude Code programmatically: Get structured output — --json-schema вместе с --output-format json и ответ по схеме в поле structured_output.
