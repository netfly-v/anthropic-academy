Простыми словами

Большое ревью: проходы по файлам и интеграционный проход

Чем больше файлов в одном запросе, тем меньше внимания достаётся каждому: модель пропускает ошибки и противоречит сама себе. Документация называет это context rot: с ростом числа токенов падают точность и полнота, даже если всё помещается в окно. Поэтому ревью строят как цепочку промптов (prompt chaining):

  1. Локальные проходы — отдельный запрос на каждый файл, все параллельно. Кроме замечаний, каждый возвращает справку: что файл отдаёт другим модулям, какие данные читает и пишет.
  2. Интеграционный проход — отдельный запрос после всех локальных. Он получает справки и замечания, а не весь код, ищет ошибки на стыках (как данные идут между модулями и где их понимают по-разному) и сводит замечания в один список без повторов и противоречий.

На экзамене большое ревью разбивают явной цепочкой проходов — так и отвечайте. По документации (на ноябрь 2026) с адаптивным мышлением и субагентами многошаговые рассуждения Claude в основном ведёт сам, а явная цепочка нужна, когда надо видеть промежуточные результаты или задать строгий конвейер — например, в своём CI.

Открытая задача: план, который меняется

Цепочка с заданными шагами годится, когда подзадачи известны заранее. В открытой задаче — скажем, покрыть тестами старый сервис — они появляются по ходу:

  1. составить карту: модули, точки входа, связи, где тесты уже есть;
  2. найти места, где тесты дадут больше всего: код рискованный, часто меняется и не покрыт;
  3. выстроить очередь от самого важного и после каждого шага пересобирать её по находкам.

Если модуль сам обращается к базе и тест для него не написать, появляется новая подзадача — вынести обращение за интерфейс, — и она встаёт в плане раньше тестов. Следующий шаг выбирают по находкам, а не по списку, составленному вслепую.

Обращение клиента с несколькими проблемами

Клиент пишет в одном сообщении о трёх проблемах; типичный провал — агент решает первую и забывает остальные. Правильно:

  1. разбить обращение на отдельные пункты;
  2. расследовать их параллельно (например, несколькими вызовами инструментов в одном ответе) с общим контекстом: кто клиент, какой у него договор, что уже проверено — иначе каждое расследование начинает с нуля и выводы расходятся;
  3. согласовать находки и дать одно решение и один ответ по всем пунктам, а не три ответа подряд.

Пример

Финтех-команда проверяет каждый pull request (PR) в CI: скрипт отправляет весь diff Claude одним запросом. PR переводит суммы из рублей с копейками в целые копейки и затрагивает 22 файла. Ревью нашло мелочи, но пропустило главное: модуль отчётов по-прежнему ждёт рубли, и суммы в выгрузке выросли в сто раз. Ни в одном файле по отдельности ошибки нет — она между файлами.

Архитектор делает два прохода. Сначала каждый изменённый файл проверяется отдельным запросом, все параллельно; ответ структурированный — замечания и справка, какие суммы файл принимает и отдаёт и в каких единицах. Затем отдельный запрос по всем справкам и замечаниям проверяет поток данных: везде ли одни единицы, нет ли двойного пересчёта. В PR уходит только его сводный список.

Как это спрашивают

Ситуации: ревью пропускает ошибку на стыке модулей; агент держится плана, составленного до первой находки; агент поддержки отвечает только на часть обращения. Неверные ходы:

  • Модель покрупнее или окно побольше. Код и так помещается; беда в том, что один запрос держит в фокусе слишком много.
  • Правило в промпте («проверяй каждый файл одинаково тщательно»). Внимания не прибавится: в запросе всё тот же diff целиком.
  • Только проходы по файлам. Ошибки между файлами им не видны: нужен интеграционный проход.
  • Полный план заранее и строгое следование ему: зависимости, найденные по ходу, в план не попадают.
  • Цепочка исполнителей, где каждый пересказывает результат следующему: подробности теряются.
  • Попросить клиента писать о каждой проблеме отдельно: работа перекладывается на клиента, связь между пунктами теряется.

Верный ход меняет саму схему работы: отдельные проходы, план по находкам, общий контекст и один ответ.

Документация

  • Prompting best practices: Chain complex prompts — когда явная цепочка запросов ещё нужна; самый частый вариант — черновик, ревью по критериям, доработка.
  • Prompting best practices: Subagent orchestration — образец промпта: субагенты — для параллельных независимых задач, а там, где контекст нужен между шагами, лучше работать без делегирования.
  • Context windows — context rot: с ростом числа токенов падают точность и полнота.
  • Parallel tool use — несколько блоков tool_use в одном ответе; независимые вызовы на чтение можно выполнять одновременно.
  • Orchestrate subagents at scale with dynamic workflows — пример «ревьюер на каждый изменённый файл, затем один ранжированный список без дублей».
  • Building effective agents — фон (Anthropic Engineering): prompt chaining, sectioning, orchestrator-workers (подзадачи определяются под конкретный вход) и агенты, которые на каждом шаге сверяются с результатами.
