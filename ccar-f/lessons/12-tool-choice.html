tool_choice и структурированный вывод

Домены 2 и 4 · подпункты 2.3, 4.3

Что уже есть в курсах

  • API · Схемы инструментов — из чего состоит определение инструмента и его input_schema.
  • API · Блоки сообщения — как разобрать ответ из блоков text и tool_use.
  • Tool use · Strict tool use: перестаньте отклонять свои же вызовы — strict: true, null для факта, которого нет в запросе, связка any + strict и модели, отклоняющие принудительный выбор.
  • API · Fine-grained tool calling — пояснение о принудительном tool_choice и ошибке 400 на новых моделях.
  • API · Маршрутизация — пояснение: схема с enum, чтобы получить ровно одну категорию.
  • API · Структурированные данные — JSON через prefill и stop sequence: старый способ; на Claude 4.6 и новее prefill даёт ошибку 400.

Простыми словами

Если нужны данные строгой формы, опишите эту форму как инструмент. Инструмент извлечения ничего не выполняет: его input_schema и есть целевая структура, а результат — поле input блока tool_use в ответе. При strict: true это поле совпадает со схемой (исключения — в уроке о strict).

Вызов определяет параметр tool_choice:

  • {"type": "auto"} — по умолчанию: Claude сам решает, вызвать инструмент или ответить текстом. При извлечении вместо данных может прийти пересказ.
  • {"type": "any"} — обязан вызвать один из инструментов, но какой — решает сам.
  • {"type": "tool", "name": "…"} — обязан вызвать именно этот.

Правило выбора:

  • Тип документа заранее неизвестен — заводят по инструменту извлечения на каждый вид и ставят any: вызов гарантирован, а по имени инструмента код узнаёт тип документа.
  • Определённый шаг должен идти первым — его инструмент выбирают по имени в первом запросе, следующие — с auto (tool_choice задают в каждом запросе заново).

В схеме:

  • Обязательное или необязательное. В required — только то, что есть в каждом документе этого вида; если поля в источнике может не быть, разрешают null.
  • enum с запасным выходом. Без него непредусмотренный случай попадёт в ближайшую, но неверную категорию. "other" с полем для уточнения показывает новые категории для списка; "unclear" — честный ответ на неоднозначный документ, который код передаст человеку.
  • Правила нормализации — в промпте. Схема со strict гарантирует форму (строка формата date, сумма — число), но не объясняет, как читать «03/04/26» или «1 234,50». Это пишут в промпте или в описании поля.

Пример

Бухгалтерия сети стоматологий получает от поставщиков PDF: счета, накладные, акты услуг. Первая версия — один инструмент и auto — иногда отвечала текстом «Это счёт от…», обучение персонала относила к «оборудованию», а без договора вписывала в обязательный «Номер договора» номер счёта. Архитектор:

  • заводит три инструмента — save_invoice, save_waybill, save_service_act — и ставит any;
  • разрешает null для номера договора, добавляет в категории расхода "other" с полем category_note и "unclear", а документы с "unclear" — на ручную проверку;
  • пишет в промпте: дату читать по стране поставщика и записывать в ISO 8601, запятая в суммах российских документов — десятичный разделитель;
  • на этапе сверки первый запрос отправляет с {"type": "tool", "name": "read_requisites"}, следующие — с auto: проверки контрагента и лимита идут по реквизитам из документа.

Как это спрашивают

В вопросе конвейер извлечения получает текст вместо данных, неверную категорию или выдумку либо агент путает порядок шагов. Заманчивые ошибки:

  • «Всегда вызывай инструмент» в промпте при auto — просьба, а не гарантия.
  • Выбор по имени при неизвестном типе документа — счёт натянут на схему акта; нужен any. И наоборот, any для обязательного первого шага — первым может оказаться не тот инструмент.
  • Принудительный выбор на каждом ходу — агент не сможет закончить текстовым ответом; принуждают только первый шаг.
  • «Ответь чистым JSON», повторы, регулярные выражения, модель покрупнее — лечат симптом; форму гарантирует схема со strict.
  • Свободная строка вместо enum или числовая «уверенность» вместо "unclear" — категории расползаются, а порог неясен.

Правильный ход — разделить гарантии: tool_choice отвечает за вызов, схема — за форму, null, "other" и "unclear" — за честность, промпт — за чтение источника.

Курс vs экзамен

Экзамен считает any и выбор по имени штатными режимами. На ноябрь 2026 Fable 5.2 и 5.1, Mythos 5.2 и 5.1, Opus 5.5 и Sonnet 5.5 отвечают на них ошибкой 400. Для них документация советует auto со strict: true и указанием в промпте, а если в фиксированном JSON нужен сам ответ — structured outputs (output_config.format). Haiku 5.5 и Opus 5 принудительный выбор принимают. На экзамене отвечайте по смыслу режимов.

Документация

  • Define tools — значения tool_choice и модели, которые не принимают принудительный выбор.
  • Strict tool use — поле input блока tool_use строго следует input_schema.
  • Structured outputs — JSON outputs через output_config.format, обязательные поля, enum, форматы строк вроде date и случаи, когда вывод всё же не совпадает со схемой.
  • Errors — ошибки 400 на принудительный tool_choice и на prefill и чем их заменить.
  • Reduce hallucinations — разрешить Claude признать, что данных не хватает (идея значения "unclear").
  • Increase output consistency — точно задавать формат вывода в промпте; для гарантии схемы — structured outputs.
