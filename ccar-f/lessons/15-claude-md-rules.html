Иерархия CLAUDE.md и .claude/rules/

Домен 3 · подпункты 3.1, 3.3

Что уже есть в курсах

  • Claude Code · CLAUDE.md, которому следуют — четыре места для CLAUDE.md; импорты через @ не экономят контекст; правило в .claude/rules/ с полем paths загружается только для подходящих файлов.
  • API · Claude Code в работе — память проекта, локальная и пользовательская; в «Пояснении» — /memory и /context.
  • Claude Code 101 · Файл CLAUDE.md — CLAUDE.md проекта и пользователя; импорт через @ загружает файл целиком в каждую сессию.

Простыми словами

Кроме уровней пользователя (~/.claude/CLAUDE.md) и проекта (./CLAUDE.md или ./.claude/CLAUDE.md), есть уровень каталога — CLAUDE.md в подкаталогах:

  • файлы из каталога запуска и всех каталогов выше загружаются при старте сессии;
  • файл подкаталога — по требованию: когда Claude читает, создаёт или правит любой файл в этом подкаталоге;
  • файлы не перекрывают друг друга, а складываются; при противоречии Claude может выбрать любое из них.

Большой файл — на темы. Вместо одного CLAUDE.md на сотни строк — файлы в .claude/rules/, по одной теме на файл. Правило без paths загружается при старте, как сам CLAUDE.md: разбиение наводит порядок, а контекст экономит поле paths.

Импорты по выбору владельцев пакета. Общие стандарты лежат в одной папке, а CLAUDE.md каждого пакета импортирует через @ только нужные ему (путь считается от импортирующего файла). Выбирают их владельцы пакета — они знают его предметную область. Импорт загружается вместе с подключившим его файлом, поэтому стандарты пакета попадают в контекст, только когда Claude работает в этом пакете.

Правило выбора:

  • соглашение привязано к месту (пакет, подсистема) — CLAUDE.md в этом каталоге, его ведут владельцы каталога;
  • соглашение привязано к типу файлов, разбросанных по репозиторию (тесты, миграции), — правило в .claude/rules/ с glob-шаблоном в paths, например **/*.spec.ts. Это один файл, и загружается он, когда Claude читает или правит подходящий файл в любом каталоге.

Диагностика. Соглашение соблюдается в одной сессии и нарушается в другой — сначала проверьте, какие файлы памяти загружены (на экзамене — /memory), потом формулировку правила.

Пример

Монорепозиторий маркетплейса: пакеты checkout и catalog. Корневой CLAUDE.md разросся до 700 строк, в нём же правила работы с деньгами. Соглашение о тестах команда checkout записала в packages/checkout/CLAUDE.md. Жалобы: тесты то по правилам, то нет; в catalog Claude применяет правила работы с деньгами.

Что делает архитектор:

  1. Проверяет через /memory, что загружено: соглашение о тестах было в контексте, только если сессию запустили внутри packages/checkout или Claude уже работал там с файлом.
  2. Переносит его в .claude/rules/testing.md с glob-шаблоном, чтобы правило загружалось для тестов любого пакета: 
    ---
paths:
  - "**/*.spec.ts"
---
  3. Разбирает корневой файл: общее (команды сборки, формат коммитов) остаётся, остальное по темам уходит в .claude/rules/, например в api-design.md.
  4. Правила работы с деньгами выносит в docs/standards/money.md. Владельцы checkout подключают его строкой @../../docs/standards/money.md в своём CLAUDE.md; в catalog импорта нет.

Как это спрашивают

Типичные ситуации: файлы одного типа в разных каталогах, разросшийся CLAUDE.md, монорепозиторий с разными стандартами пакетов, разное поведение сессий. Соблазнительные неверные ходы:

  • Копия соглашения в CLAUDE.md каждого каталога — копии расходятся, загружаются, даже когда Claude правит не тест, а какой-нибудь каталог останется без своей.
  • Всё в одном файле плюс пометки IMPORTANT — длинный файл соблюдается хуже.
  • Соглашение в skill — skill загружается по вызову или когда Claude сочтёт его уместным, а правило с paths — само, по пути файла.
  • Импорты «для экономии контекста» — импорт контекст не экономит; экономят paths и CLAUDE.md подкаталогов.
  • Правила команды в ~/.claude/CLAUDE.md — личный файл не попадает в git и действует только у владельца.
  • Модель посильнее или повтор правила в промпте — если файл не загружен, дело не в модели.

Верный ход — положить инструкцию туда, откуда она загрузится ровно тогда, когда нужна.

Курс vs экзамен

На экзамене загруженные файлы памяти проверяют через /memory — так и отвечайте. В курсе API для этого названа /context, и это ближе к продукту: на ноябрь 2026 /memory только показывает, где лежат файлы памяти пользователя и проекта, открывает их в редакторе и переключает auto memory, а загруженное при старте перечисляет /context all. CLAUDE.md подкаталога там нет: он загружается по требованию, и в терминале появляется строка Loaded с его путём.

Документация

  • How Claude remembers your project: How CLAUDE.md files load — каталоги выше загружаются при старте, подкаталоги — по требованию; файлы складываются, а не перекрывают друг друга.
  • How Claude remembers your project: Import additional files — синтаксис @path, путь от импортирующего файла.
  • How Claude remembers your project: Set up rules — .claude/rules/, по одной теме на файл, подпапки; правила без paths загружаются при старте; skills, в отличие от правил, — по вызову или когда Claude сочтёт их уместными.
  • How Claude remembers your project: Path-specific rules — поле paths и glob-шаблоны; правило загружается, когда Claude читает или правит подходящий файл.
  • How Claude remembers your project: Write effective instructions — меньше 200 строк на файл; импорты не уменьшают расход контекста.
  • How Claude remembers your project: View and edit with /memory — что перечисляет и что умеет /memory.
  • How Claude remembers your project: Troubleshoot memory issues — /context all и строка Loaded для подкаталогов.
  • Set up Claude Code in a monorepo or large codebase — CLAUDE.md по пакетам, их ведут владельцы каталогов; таблица «per-directory CLAUDE.md или path-scoped rule».
  • Debug your configuration — /context показывает загруженное, /memory — места файлов памяти.
  • Commands — описания /memory и /context [all].
