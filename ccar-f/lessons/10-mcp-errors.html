Ошибки MCP-инструментов

Домен 2 · подпункт 2.2

Что уже есть в курсах

  • API · Инструменты в MCP — исключение в инструменте становится результатом с isError, и Claude видит его текст.
  • MCP · Инструменты в MCP — проверка ID документа; в пояснении — как в SDK версии 2 передать Claude текст ошибки.
  • API · Функции-инструменты — проверка входных данных и понятное сообщение, по которому Claude повторит вызов с исправленными параметрами.
  • API · Реализация цикла — даже при сбое инструмента в ответ уходит блок результата с is_error.
  • Tool use · Инструменты, которые выбирает Claude — «Error 404» Claude ничего не подсказывает, а сообщение с подсказкой помогает исправить вызов.
  • Tool use · Параллельные вызовы инструментов: меньше задержка — в ошибке говорится, что пошло не так и что попробовать дальше.

Простыми словами

Курсы учат главному: ошибка — тоже ответ, и Claude его читает. Экзамену важно другое: что агенту делать дальше — повторить, исправить аргументы, объяснить отказ или позвать человека. Из «Something went wrong» этого не понять, и агент гадает: повторяет вызов, который не пройдёт никогда, или сдаётся там, где хватило бы паузы.

Поэтому сервер различает четыре вида сбоев:

  • Временный (transient) — внешняя система не ответила вовремя, перегружена или упёрлась в лимит запросов. Повтор имеет смысл, лучше с паузой; сообщение говорит, когда повторить.
  • Неверные входные данные (validation) — дата в прошлом, номер в неверном формате. Повтор без правки бесполезен; сообщение говорит, что исправить.
  • Бизнес-правило (business) — запрос корректен, но его запрещают правила компании. Повтор не поможет: агент объясняет человеку причину и предлагает другой путь.
  • Нет прав (permission) — доступа нет у агента или пользователя. Повтор тоже не поможет: нужен другой маршрут, например передача человеку.

Ответ об ошибке должен сам сказать агенту три вещи: вид ошибки, стоит ли пробовать снова (отдельным полем «да/нет», а не намёком в тексте) и что случилось — словами, понятными человеку. К отказу по правилам компании добавьте готовую фразу для клиента — вежливую, без внутренних кодов, иначе агент сочинит причину сам.

Стандартных полей для этого на ноябрь 2026 нет: и в MCP, и в Claude API у ошибки есть только признак (isError / is_error), а вид и флаг сервер кладёт в содержимое результата в своём формате, поэтому на экзамене имена полей могут быть другими.

Отдельная ловушка — пустой результат. Поиск, который отработал и ничего не нашёл, — это успех: isError не ставится, а в тексте сказано, что искали и что совпадений нет. И наоборот: если база не ответила, пустой список возвращать нельзя — агент уверенно скажет клиенту «ничего нет», хотя даже не смог проверить.

Пример

В сети клиник запись на приём ведёт агент через MCP-сервер расписания с инструментами search_slots (свободные окна врача) и move_visit (перенос приёма). Первая версия сервера на любое исключение отвечает «Something went wrong». В логах три случая:

  • база расписания на секунду не ответила — агент сказал пациенту, что перенос невозможен;
  • пациент хотел перенести приём за час до начала, а онлайн-перенос закрывается за 2 часа — агент пять раз повторил тот же вызов;
  • у врача не было окон на выбранную дату, и сервер вернул это как ошибку — агент ответил «система недоступна».

Архитектор переделывает ответы сервера. Таймаут сервер сначала повторяет сам, а если не помогло, отдаёт временную ошибку с пометкой, через сколько повторить. Пустой поиск — успешный ответ «на 24 ноября свободных окон нет», и агент предлагает соседние даты. Отказ из-за правила о сроках выглядит так:

{
  "category": "business",
  "retryable": false,
  "detail": "Rebooking closes 2 hours before the visit",
  "customer_message": "Перенести приём онлайн можно не позднее чем за 2 часа. Могу передать запрос в регистратуру."
}

Объект лежит текстом в результате с isError: true: retryable: false останавливает повторы, а customer_message агент передаёт пациенту.

Как это спрашивают

В вопросе агент зря повторяет вызовы, сдаётся при коротком сбое или путает «ничего не найдено» с «не удалось проверить». Заманчивые, но неверные ходы:

  • Правило в промпте («при ошибке повтори не больше трёх раз»): агент всё равно не знает вида ошибки и одинаково повторит и таймаут, и запрет по правилам компании.
  • Один счётчик повторов в коде на все ошибки: попытки уходят на то, что не пройдёт никогда.
  • Модель покрупнее: никакая модель не выведет причину из «Something went wrong».
  • Пустой список вместо ошибки при сбое — или, наоборот, isError на пустой поиск.

Верный ход — на стороне инструмента: причину сбоя знает только сервер, поэтому он сам передаёт вид ошибки, флаг повтора и понятное описание.

Документация

  • MCP Specification (2026-07-28): Tools — Error Handling — ошибки протокола (JSON-RPC) и ошибки выполнения с isError: сбои API, неверный ввод, бизнес-логика; ошибки выполнения клиенту следует передавать модели.
  • Handle tool calls: Handling errors with is_error — инструктивные сообщения вместо «failed», пример с подсказкой, когда повторить; при неверном вызове Claude делает 2–3 попытки, прежде чем извиниться.
  • Writing effective tools for agents — with agents — фон (Anthropic Engineering): в ответе об ошибке — конкретные подсказки, а не непрозрачные коды и трассировки.
