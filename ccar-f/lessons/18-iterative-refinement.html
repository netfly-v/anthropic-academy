Простыми словами

Доработка с Claude Code — цикл «сделал — получил обратную связь — исправил». Документация Claude Code называет две частые причины неудачи: Claude не хватило сведений, которых нет в коде, или ему нечем было проверить свою работу. Отсюда пять приёмов.

  • Интервью до работы. В незнакомой области не видно даже, какие решения предстоят. Попросите Claude сначала расспросить вас: он задаёт вопросы с вариантами ответа (инструмент AskUserQuestion) — когда сбрасывать кеш, что делать при отказе внешнего сервиса. Так всплывает то, о чём вы не подумали. Ответы сводят в спецификацию, а код по ней пишут в новой сессии.
  • Примеры вместо описания. Если Claude от раза к разу по-разному понимает словесное описание преобразования, дайте 2–3 разные пары «вход — ожидаемый выход», включая пограничные случаи. На ноябрь 2026 документация и курс API советуют 3–5 примеров, но решает конкретность пар, а не их число.
  • Тесты до кода — не только на обычный случай. Тесты описывают ожидаемое поведение, пограничные случаи (пустое значение, граница диапазона, неверный ввод) и требования к скорости: чего нет в тестах, Claude не проверит. Запускает их сам Claude; если тест упал у вас, например в CI, передайте Claude его вывод, а не «не работает». Просите общее решение, а не подгонку под тестовые данные.
  • Конкретный случай для пограничной ошибки. Вместо «обработай пустые значения правильно» — точный вход и ожидаемый результат, лучше падающим тестом: так вы заранее говорите, как выглядит «исправлено».
  • Одно сообщение или по очереди. Если проблемы связаны (исправление одной меняет поведение другой), опишите их в одном подробном сообщении, иначе Claude чинит одно, ломая другое, и правки ходят по кругу. Независимые проблемы исправляйте по одной: каждую правку легко проверить и откатить.

Пример

Команда бухгалтерского сервиса поручает Claude Code импорт банковских выписок из CSV с пересчётом валют по курсам из внешнего источника; кешировать курсы ей раньше не приходилось. Просьбу «приведи суммы к единому формату» Claude каждый раз понимает по-своему: «1 234,50» превращается то в 1234.50, то в 123450.

  1. Интервью. «Расспроси меня о кеше курсов и запиши спецификацию в SPEC.md». Claude спрашивает, сколько действует курс и что делать, если источник не отвечает: останавливать импорт или брать вчерашний курс с пометкой.
  2. Примеры. 1 234,50 → 1234.50; возврат (120,00) → -120.00; пустое поле → null.
  3. Тесты до кода. Обычные строки, пустая сумма, возврат в скобках, дата 29 февраля и скорость: файл на 200 000 строк — меньше чем за минуту. Затем: «Пиши код, пока тесты не пройдут».
  4. Разбор ошибок. На настоящей выписке у валютных возвратов теряется знак и на копейку сбивается округление. Обе ошибки — в одном шаге обработки суммы, и округление зависит от того, когда восстановлен знак, поэтому их подают одним подробным сообщением с входными строками и ожидаемыми суммами. Неверный заголовок колонки в отчёте об ошибках ни с чем не связан и правится отдельно.

Как это спрашивают

Типичная ситуация: результаты непоследовательны, ломается пограничный случай, задача из незнакомой области или после прогона всплыло несколько ошибок. Соблазнительные неверные ходы:

  • Описать подробнее и строже. Описание и так понимают по-разному; пример не рассказывает, а показывает.
  • Модель покрупнее или effort повыше. Не хватает сведений, а не ума.
  • В незнакомой области сразу браться за реализацию. Решения, которых вы не заметили, Claude примет молча, и они всплывут уже в продакшене.
  • Всегда всё одним сообщением или всегда по одной проблеме. Решает связь между проблемами.

Верный ход — дать Claude недостающие сведения в проверяемом виде: ответы на интервью, примеры, тесты, конкретные падающие случаи.

Документация

  • Best practices for Claude Code: Write a specific prompt — назвать файл и симптом, сказать заранее, как выглядит «исправлено»; готовое отдавать, а не описывать.
  • Best practices for Claude Code: Brainstorm with Claude first — интервью вопросами с вариантами ответа, спецификация в SPEC.md, сборка в новой сессии.
  • Best practices for Claude Code: Give Claude a check to run — проверка «прошло / не прошло», по которой Claude сам замыкает цикл; просить доказательство — команду и её вывод.
  • Tools reference: AskUserQuestion tool behavior — вопросы с вариантами ответа, чтобы собрать требования и снять неоднозначность.
  • Common workflows: Work with tests — тесты на пограничные условия; Claude может предложить случаи, которые вы упустили.
  • Common workflows: Refactor code — изменения небольшими проверяемыми шагами.
  • Prompting best practices: Use examples effectively — примеры повышают точность и единообразие; они должны быть уместными, разнообразными и структурированными, 3–5 штук.
  • Prompting best practices: Avoid focusing on passing tests and hardcoding — тесты проверяют правильность, а не определяют решение; просить общее решение без подгонки под тестовые данные.
