Описания инструментов: разделить, переименовать, развести

Домен 2 · подпункты 2.1, 2.4

Что уже есть в курсах

  • Tool use · Инструменты, которые выбирает Claude — Claude выбирает инструмент по описанию; что в нём писать, включая «когда не вызывать»; пересекающиеся инструменты объединяют в один с параметром; правки проверяют оценкой (eval).
  • Platform 101 · Что такое tool use — Claude сопоставляет запрос с описаниями и так различает похожие инструменты; расплывчатое описание — главная причина ошибок.
  • API · Схемы инструментов — name, description, input_schema и правила хорошего описания.
  • MCP · Инструменты в MCP — описания MCP-инструмента и его аргументов пишут в коде сервера, и из них SDK собирает то, что видит Claude.

Простыми словами

Claude выбирает инструмент по тексту: именам, описаниям и вашему системному промпту. API собирает всё это в один системный промпт, поэтому одно может перебить другое. Четыре приёма, которых нет в курсах:

1. Переименовать пересекающиеся. Если имена почти синонимы (search и find), Claude выбирает наугад. Дайте каждому имя, в котором видны источник и действие, а в описании укажите, когда его вызывать, когда нет и что взять вместо.

2. Разделить универсальный. Инструмент «сделай что-нибудь с документом» с параметром режима прячет разные задачи под одним описанием, и Claude не знает, что получит. Замените его узкими: у каждого заранее понятно, что подать на вход и что придёт в ответ. В MCP форму ответа закрепляет поле outputSchema: сервер обязан вернуть structuredContent по этой схеме.

3. Проверить промпт на слова-триггеры. Модели понимают указания буквально, поэтому правило «увидел слово X — вызывай Y» срабатывает и там, где нужен другой инструмент, и перебивает хорошее описание. По документации, резкие формулировки вроде «CRITICAL: You MUST use this tool» приводят к лишним вызовам. При ревью заменяйте такие правила описанием ситуации и цели.

4. Объяснить, чем MCP-инструмент лучше встроенного поиска. Встроенный поиск Claude Code (инструмент Grep, а на ноябрь 2026 на macOS, Linux и WSL по умолчанию — команды grep и find через Bash) хорош для текста в локальных файлах. Если MCP-инструмент знает то, чего в файлах нет, а описание об этом молчит, у Claude нет причины его выбрать. Напишите, что умеет только он, что возвращает и когда он лучше grep; ключевые слова — в начало описания и в server instructions.

Пример

Команда настроила Claude Code как помощника дежурных инженеров. Через месяц — жалобы:

  • на вопрос «есть ли ранбук для ошибки 502?» агент роется в логах;
  • инструмент inspect с параметром what (логи, метрики, релизы) отдаёт то строки, то ряды чисел, и агент путает ответы;
  • на вопрос «включён ли флаг fast-retry в проде?» агент ищет grep по репозиторию и находит только значение по умолчанию, хотя MCP-сервер flags знает текущее состояние.

Что делает архитектор:

  1. Заменяет в системном промпте строку «если есть слово „ошибка“ — ищи в логах» целью: «логи — для текущего сбоя, готовые решения — в ранбуках».
  2. Переименовывает общий search в search_runbooks: «только ранбуки и разборы инцидентов; логи не ищет».
  3. Делит inspect на search_service_logs (сервис, интервал, текст → строки лога), get_metric_series (метрика, интервал → ряд значений) и list_recent_releases (сервис → версии и время).
  4. Дописывает в описание get_flag_state: «текущее значение флага в каждом окружении; в коде только значения по умолчанию, поэтому „включён ли сейчас“ — сюда, а не в grep».
  5. Сравнивает результаты оценки до и после правок.

Как это спрашивают

Типичная ситуация: агент вызывает не тот инструмент, «универсальный» ведёт себя непредсказуемо или агент обходит MCP-сервер. Соблазнительные неверные ходы:

  • «ВСЕГДА используй X» в промпте — новый триггер: лишние вызовы, а пересечение остаётся.
  • Модель покрупнее — дело в определениях, а не в модели.
  • Один инструмент с режимом — двусмысленность переезжает в параметр.
  • Маршрутизатор по ключевым словам в коде — громоздко для первого шага и по сути тот же триггер «по слову».
  • Принудительный tool_choice — выбор по смыслу так не наладить, а на новейших моделях (на ноябрь 2026) это ошибка 400.
  • Запрет встроенного поиска — Claude теряет нужный инструмент, а бедное описание остаётся.

Верный ход — править текст, который читает Claude: имена, границы инструментов, промпт, описание MCP-инструмента. Если же вызов обязателен всегда, гарантию дают код или tool_choice («tool_choice»), а не описания.

Курс vs экзамен

Курс Tool use и документация (на ноябрь 2026) советуют объединять родственные операции над одним объектом, а экзамен ждёт, что «универсальный» инструмент разделят. Противоречия нет: объединяют почти одинаковые инструменты, а делят тот, что прячет разные задачи с разными результатами.

Документация

  • Define tools: Best practices for tool definitions — подробное описание, «когда не использовать», объединение родственных операций, префиксы в именах; раздел Tool use system prompt — описания и ваш промпт собираются в один системный промпт; таблица про tool_choice — промпт влияет на выбор инструмента, принудительный вызов на новейших моделях даёт 400.
  • Troubleshooting tool use: Claude calls the wrong tool — различать инструменты по тому, когда их вызывать; совпадение имён и слишком общая схема.
  • Prompting best practices: Tool usage — точное следование указаниям; резкие формулировки вроде «CRITICAL: You MUST use this tool» приводят к лишним вызовам.
  • Prompting best practices: Overthinking and excessive thoroughness — «Default to using [tool]» и «If in doubt, use [tool]» заменить точными условиями.
  • Prompting Claude Sonnet 5: More literal instruction following — модель понимает указания буквально и не обобщает их сама.
  • Connect Claude Code to tools via MCP: Scale with MCP tool search — отложенные MCP-инструменты, server instructions, ключевые слова в начале описания, лимиты длины, alwaysLoad.
  • Tools reference: Glob tool behavior — Grep и Glob отсутствуют по умолчанию на macOS, Linux и WSL, поиск идёт через Bash.
  • MCP specification (2026-07-28): Tools — поля описания инструмента, outputSchema и structuredContent.
  • Writing effective tools for agents — with agents — фон (Anthropic Engineering): у каждого инструмента — ясное отдельное назначение; лишние и пересекающиеся инструменты отвлекают агента от эффективной стратегии.
