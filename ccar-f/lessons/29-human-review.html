Проверка человеком и калибровка уверенности

Домен 5 · подпункт 5.5; домен 4 · подпункт 4.6

Что уже есть в курсах

Самой темы в курсах нет. Ближе всего — уроки об оценке промптов:

  • API · Типичный процесс оценки — датасет, грейдер, сравнение версий промпта по среднему баллу.
  • API · Генерация тестового датасета — набор тестовых задач для прогонов.
  • API · Оценка с помощью модели — грейдеры на коде, на модели и люди-оценщики.

Простыми словами

Система извлекает данные из документов, и надо решить, что принимать без проверки человеком. Решают по измерениям, а не на глаз.

  • Одна цифра обманывает. Общая точность 98% — это среднее. Если большая часть потока — типовые счета, редкий тип документа или трудное поле может проваливаться незаметно. Поэтому точность считают по каждому типу документа и каждому полю, а проверку убирают только в тех сегментах, где цель достигнута.
  • Уверенность калибруют. Модель может вернуть оценку уверенности для каждого поля, а не одну на документ. Схема structured outputs гарантирует, что поле confidence будет числом, но не гарантирует, что это число что-то значит. Его калибруют на размеченном наборе — документах, где верный ответ заранее проставили люди: смотрят, как часто модель права при каждом уровне уверенности, и ставят порог там, где ошибок не больше допустимого. У каждого поля порог свой.
  • Что отдавать людям. Поля ниже порога и документы с неоднозначным или противоречивым источником (две разные суммы в одном счёте), даже если модель уверена. Людей мало, поэтому очередь сортируют: сначала случаи, где ошибка дороже всего, и самые сомнительные.
  • Уверенные ответы тоже проверяют. Небольшую случайную выборку берут из каждого слоя — типа документа, поля, диапазона уверенности. Это стратифицированная выборка: в простой случайной редкие типы почти не попадаются. Она показывает реальный процент ошибок среди «уверенных» и ловит новые виды сбоев, например когда поставщик сменил шаблон документа.

Тот же приём работает в ревью кода: отдельный проход ставит каждому замечанию балл уверенности, уверенные замечания сразу уходят в pull request, сомнительные — инженеру. Границу калибруют по прошлым замечаниям, про которые известно, подтвердились ли они.

Пример

Логистическая компания разбирает счета, транспортные накладные и таможенные декларации. Агент извлекает поставщика, сумму, валюту, код товара и даты. За месяц точность — 98%, и руководитель хочет перестать проверять всё, в чём модель уверена.

Архитектор сначала строит таблицу «тип документа × поле»: в декларациях код товара верен лишь в 84% случаев — в среднем этого не видно. Дальше:

  1. счета и накладные, где каждое поле достигает цели, переводят на автоматический приём; декларации остаются под проверкой;
  2. на 600 размеченных документах подбирают порог уверенности для каждого поля;
  3. поля ниже порога и документы, где цифры расходятся, уходят в очередь проверяющих, крупные суммы — первыми;
  4. из автоматически принятого каждую неделю проверяют случайную выборку по каждому типу документа; найденные ошибки пополняют размеченный набор, и пороги пересчитывают.

Как это спрашивают

В вопросе обычно высокая общая точность и надо решить, где убрать человека, или проверяющие не справляются с очередью. Соблазнительные ошибки:

  • Поверить общей цифре и автоматизировать всё.
  • Порог «на глаз», например 0,9, без калибровки на размеченном наборе.
  • Не проверять уверенные ответы или брать простую случайную выборку вместо стратифицированной.
  • Модель покрупнее, повторы или «будь внимательнее» в промпте — они не показывают, где ошибки: это задача измерения, а не генерации.
  • Всё отдать людям — их время берегут для рискованного и спорного.

Начинают с того, что закрывает проблему из вопроса: решают, где убрать человека, — с разбивки точности по сегментам; проверяющие тонут в очереди — с откалиброванных порогов и приоритетов.

Курс vs экзамен

Курс API сравнивает версии промпта по среднему баллу, а документация об оценках (на ноябрь 2026) советует по возможности обходиться без людей-оценщиков. Оба совета — про отладку промпта на тестовом наборе. В продакшене одного среднего мало, а люди нужны для разметки проверочного набора, выборочной проверки и спорных случаев.

Документация

  • Define success criteria and build evaluations — измеримые критерии, отложенный тестовый набор, примеры с разметкой людей, трудные случаи; способы оценки: код, модель и люди (людей советует избегать: медленно и дорого).
  • Ticket routing — критерии успеха с точностью по сегментам: по языкам, на трудных случаях, по группам клиентов.
  • Structured outputs — пример схемы с числовым полем confidence; гарантированы только формат, типы полей и обязательные поля, а не верность значений.
  • Reduce hallucinations — разрешить модели сказать «не знаю», требовать подтверждающую цитату; критичное всё равно проверять.
  • Content moderation — уровни риска по уверенности модели: высокий риск блокируют автоматически, пользователей с частыми сообщениями среднего риска отдают на проверку людям.
