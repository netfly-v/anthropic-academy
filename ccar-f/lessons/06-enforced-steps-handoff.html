Обязательный порядок шагов и передача человеку

Домен 1 · подпункт 1.4

Что уже есть в курсах

  • Claude Code · Hooks — правило в CLAUDE.md — лишь просьба, а hook даёт гарантию; PreToolUse возвращает deny до того, как вызов выполнится.
  • Claude Code 101 · Hooks — PreToolUse блокирует опасное действие и сообщает Claude причину.
  • Tool use · Параллельные вызовы инструментов: меньше задержка — вызовы, которые меняют данные или зависят друг от друга, лучше выполнять по очереди; на пропущенный вызов отвечают tool_result с is_error: true.
  • Platform 101 · Что такое Managed Agents — политика разрешений приостанавливает чувствительное действие, пока его не одобрит человек.

Простыми словами

Некоторые шаги должны идти строго по порядку: сначала подтвердить личность клиента, потом трогать его деньги и данные. Правило в промпте — лишь просьба (см. урок Claude Code · Hooks). Если пропуск шага грозит потерей денег или данных либо нарушает закон, порядок обеспечивает код, а промпт только объясняет его.

  • Состояние хранит ваш код. Когда проверка пройдена, код записывает подтверждённый ID клиента в состояние сессии. Модель его не записывает и не стирает.
  • Барьер стоит перед инструментом. В Agent SDK hook PreToolUse — функция вашего приложения — стоит на каждом инструменте, которому нужен проверенный клиент (и на денежном, и на читающем его данные). Если клиент не подтверждён или ID в вызове чужой, hook возвращает permissionDecision: "deny", а в permissionDecisionReason пишет для Claude, какой шаг сделать сначала.
  • Свой цикл на Messages API: та же проверка перед выполнением, а вместо вызова — tool_result с is_error: true и подсказкой, что делать дальше.
  • Не canUseTool. До этого колбэка разрешений не доходят вызовы, уже одобренные правилом allowedTools или режимом bypassPermissions. PreToolUse видит и их, а его deny действует даже в bypassPermissions. canUseTool нужен, чтобы показать вызов человеку и дождаться решения.

Вторая половина темы — передача дела человеку посреди процесса. Оператор переписки не видит, и пересказ «клиент недоволен, разберитесь» заставит его начинать с нуля. Поэтому агент вызывает инструмент передачи с обязательными полями; в Messages API со strict: true входные данные всегда соответствуют схеме. В сводке:

  • подтверждённый ID клиента и суть обращения;
  • найденная причина проблемы и чем она подтверждена;
  • сумма или предмет спора;
  • что агент уже сделал и сказал клиенту;
  • почему передал: лимит, исключение из правил, просьба клиента;
  • рекомендуемое действие.

Точно известные поля (ID из состояния, суммы из учётных систем) подставляет код, модели остаются причина и рекомендация.

Пример

Агент поддержки интернет-провайдера начисляет компенсацию за перебои связи. Инструменты: verify_subscriber (номер договора и код из SMS), apply_credit и open_operator_ticket. Аудит нашёл начисления без проверки: клиент торопил агента или называл чужой договор, хотя промпт требует «сначала проверка».

  1. При верном коде обработчик verify_subscriber записывает номер договора в состояние сессии.
  2. PreToolUse на apply_credit отказывает, если подтверждения нет или договор другой: «Абонент не подтверждён. Сначала verify_subscriber». У hook задан on_failure="block" (onFailure в TypeScript): без него упавший колбэк пропускает вызов дальше, к обычной проверке разрешений.
  3. Сумму выше лимита агента тот же hook отклоняет: «Выше лимита, передай оператору». Агент открывает заявку: договор, жалоба, причина (авария на узле с 3 по 5 ноября, подтверждённая мониторингом), расчёт суммы, что сказано клиенту, рекомендация «начислить 2 400 ₽». Клиенту он сообщает, что дело передано специалисту, но сумму не обещает.

Как это спрашивают

Типичная ситуация: агент изредка пропускает обязательный шаг перед необратимым действием или операторы после эскалации заново расспрашивают клиентов. Неверные ходы:

  • Усилить промпт («ОБЯЗАТЕЛЬНО», примеры): пропусков станет меньше, но для денег и персональных данных нужен ноль.
  • Модель побольше или самопроверка («оцени уверенность, что клиент проверен»): та же вероятность, и модель проверяет сама себя.
  • Проверка задним числом (PostToolUse, ночной аудит): ошибку найдут, когда деньги уже ушли.
  • Вся переписка или свободный пересказ оператору: длинную переписку не прочтут, а в свободном тексте легко потерять сумму или ID.

Верный ход детерминированный: барьер в коде до вызова инструмента и сводка с фиксированными полями.

Курс vs экзамен

Экзамен, как и уроки Claude Code («без исключений»), считает программный барьер детерминированной гарантией. На ноябрь 2026 в Agent SDK это верно, пока колбэк не падает (шаг 2 примера); не уложившийся в таймаут PreToolUse блокирует вызов и без on_failure. На экзамене выбирайте программный барьер, а в коде ставьте on_failure="block".

Документация

  • Intercept and control agent behavior with hooks — колбэк PreToolUse: deny с причиной для Claude, onFailure: "block", таймаут блокирует вызов, session_id во входных данных.
  • Configure permissions — порядок проверки вызова: hooks, правила, режим, canUseTool; вызовы, одобренные на предыдущих шагах, до canUseTool не доходят; deny из hook действует и в bypassPermissions.
  • Handle approvals and user input — canUseTool приостанавливает вызов до ответа человека; вызов, который уже одобрило правило или режим, до него не доходит, а PreToolUse видит и такие.
  • Handle tool calls — is_error: true и совет писать в ошибке, что пошло не так и что делать дальше.
  • Strict tool use — со strict: true входные данные инструмента всегда соответствуют схеме, обязательные поля на месте.
  • Customer support agent — точность эскалации как метрика успеха; агент не даёт обещаний сверх своих полномочий.
