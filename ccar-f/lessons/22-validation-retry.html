Проверка и повтор с текстом ошибки

Домен 4 · подпункт 4.4

Что уже есть в курсах

  • Tool use · Strict tool use: перестаньте отклонять свои же вызовы — strict: true приводит вызов к схеме, бизнес-правила по-прежнему проверяет валидатор, а факт, которого нет в запросе, приходит как null.
  • Tool use · Инструменты, которые выбирает Claude — понятный текст ошибки в tool_result с "is_error": true подсказывает Claude, что исправить.
  • API · Цепочки — отдельный запрос на доработку исправляет конкретные нарушения в готовом результате.
  • API · Агенты и рабочие процессы — evaluator-optimizer: замечания оценщика возвращаются исполнителю, число итераций ограничено.
  • Claude Code · Проверка автономных запусков — hook с exit 2 передаёт Claude текст сбоя, и тот сам исправляет ошибку.

Простыми словами

При извлечении данных бывают ошибки двух видов, и лечат их по-разному.

  • Ошибки формы (синтаксические): невалидный JSON, строка вместо числа, пропущенное обязательное поле. Их устраняет схема — strict tool use или JSON outputs, повторы не нужны.
  • Ошибки смысла (семантические): JSON безупречен, но данные неверны — налог записан в поле скидки, строки в сумме не дают напечатанный итог. Схемой это не выразить: такое ловит только ваш код-валидатор после ответа.

Для ошибок смысла работает повтор с обратной связью. В новый запрос передают три вещи: исходный документ, неудачный результат и конкретные сообщения валидатора (например, Pydantic) — какое поле и что с ним не так. Это self-correction из документации о chaining, только проверяет здесь не Claude, а ваш код.

Но повтор помогает не всегда:

  • Поможет, если ответ в документе есть, а модель ошиблась с форматом, полем или структурой: пропустила строку, записала дату не в том виде.
  • Не поможет, если данных в документе нет или они в другом документе, который в запрос не попал. Факт не появится, растёт лишь риск выдумки. Такое поле в схеме допускает null, модели прямо разрешают ответить «в документе нет», а запись передают человеку или добавляют в запрос недостающий документ.

Самопроверку закладывают в схему: рядом с напечатанным итогом модель записывает итог, посчитанный по строкам, а булев флаг отмечает противоречие в самом источнике. Код сравнивает два числа: расхождение без флага — промах модели, его обычно исправляет повтор; с флагом — ошибка в документе, запись уходит человеку.

Пример

Логистическая компания разносит счета перевозчиков (PDF) в учётную систему. Claude вызывает инструмент record_carrier_invoice со strict: true; среди полей — printed_total (напечатанный итог), lines_total (сумма строк по подсчёту модели), флаг source_conflict и тариф contract_rate. Валидатор отклоняет каждый седьмой счёт; ошибок формы среди отказов нет, только ошибки смысла.

  1. Когда lines_total и printed_total расходятся, код отправляет повтор: тот же PDF, неудачный JSON и сообщение «сумма строк 48 300 ≠ напечатанный итог 51 300: проверьте, не пропущена ли строка и не попала ли доплата за топливо в другое поле». Чаще всего модель находит пропущенную строку.
  2. Если строки и после повтора дают 48 300, ошибка в самом счёте: модель ставит source_conflict: true, и счёт уходит бухгалтеру, а не на третий круг.
  3. contract_rate пустует во всех счетах «по тарифу договора»: тариф есть только в договоре, которого в запросе нет, и повторы бесполезны. Поле допускает null, код берёт тариф из базы договоров.
  4. Повторов не больше одного-двух, дальше — ручная проверка.

Как это спрашивают

Типичная ситуация: валидатор в конвейере извлечения отклоняет часть документов; одни поля повтор исправляет, другие — никогда. Соблазнительные неверные ходы:

  • Повтор без текста ошибки или без документа — модель не знает, что исправлять, или не может перечитать источник.
  • Больше повторов или более крупная модель для поля, которого в документе нет, — факт не появится, а риск выдумки вырастет.
  • Правило в промпте («проверь, что итог сходится») вместо сравнения в коде — инструкция не гарантия.
  • Поле уверенности (confidence score) — самооценка модели не проверяет арифметику, а сравнение двух чисел в коде проверяет.
  • Надежда на схему при ошибках смысла — strict гарантирует форму, а не правильность.

Верный ход: проверка в коде; повтор с документом, результатом и текстом ошибок — только для того, что в документе есть; для отсутствующего — null и человек; для противоречия в источнике — флаг.

Курс vs экзамен

Экзамен считает, что синтаксические ошибки устраняет сам tool use с JSON-схемой. По документации на ноябрь 2026 без strict Claude может прислать "2" вместо 2 или пропустить обязательное поле; гарантию дают strict: true или JSON outputs (кроме отказа и обрыва по max_tokens). На экзамене отвечайте «синтаксис обеспечивает tool use, смысл проверяет валидатор»; в продукте включайте strict.

Документация

  • Structured outputs — JSON outputs и strict tool use: валидный JSON без повторов из-за нарушений схемы; раздел Invalid outputs — отказ и обрыв по max_tokens (повторить с увеличенным лимитом).
  • Strict tool use — без strict возможны "2" вместо 2 и пропущенные обязательные поля; со strict входные данные инструмента совпадают со схемой.
  • Handle tool calls — раздел Handling errors with is_error: понятное сообщение об ошибке, и Claude повторяет вызов с исправлениями.
  • Prompting best practices: Chain complex prompts — self-correction: черновик, проверка по критериям, доработка отдельными вызовами.
  • Reduce hallucinations — разрешить ответ «не знаю» и опираться только на переданные документы.
