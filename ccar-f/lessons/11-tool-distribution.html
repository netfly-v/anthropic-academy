Сколько инструментов давать агенту

Домен 2 · подпункт 2.3

Что уже есть в курсах

  • Subagents · Эффективные субагенты — каждому субагенту дают только инструменты его роли; без поля tools он наследует все.
  • Tool use · Инструменты, которые выбирает Claude — четыре пересекающихся инструмента из шести объединили в один (стало три), и результат eval вырос с 47% до 87%; tool search для больших каталогов.
  • Platform 101 · MCP — от MCP-сервера включают только нужные инструменты (default_config, configs).
  • Claude Code · GitHub Actions и Code Review — job, который работает без присмотра, получает только нужные инструменты (--allowedTools).
  • API · Веб-поиск — allowed_domains и max_uses сужают встроенный поиск.
  • Tool use · Web search: ответы с сайтов, которым вы доверяете — поиск только по доверенным сайтам.

Простыми словами

Каждый инструмент — ещё один вариант выбора. На каждом шаге агент выбирает из всех выданных инструментов по их описаниям. Чем их больше и чем сильнее они похожи, тем чаще он берёт не тот. Из короткого списка под одну работу выбирать надёжнее, чем из всего каталога системы. Документация тоже советует: лучше меньше инструментов, но ёмких. Это не спорит с разделением «универсального» инструмента на узкие: убирают чужие и дублирующие инструменты, а разные задачи в одном не смешивают.

Чужой инструмент тянет в чужую работу. Модель считает выданный инструмент частью задачи и пользуется им, хотя промпт и критерии агента написаны под другую работу. Чужое такой агент делает хуже профильного и в обход координатора. Надёжная граница — поле tools субагента: инструмента, которого там нет, в его сессии просто нет.

Как распределять инструменты:

  • Роль — узкий набор: только то, без чего агент не сделает свою часть.
  • Частая нужда — узкая версия чужого инструмента. Простые случаи агент закроет сам, без кругов через координатора.
  • Сложный случай — через координатора. Агент сообщает в результате, что узкого инструмента мало, и координатор поручает работу нужной роли. Управление остаётся в одной точке. В Claude Code и Agent SDK на ноябрь 2026 субагент по умолчанию может сам запускать субагентов, поэтому из его tools убирают инструмент Agent (в экзамене — Task).
  • Вместо универсального — специальный. Не «открыть любой адрес», а инструмент, который принимает только то, что нужно роли, сам проверяет входные данные в коде и при отказе возвращает ошибку с причиной (is_error). У встроенного web fetch для этого есть allowed_domains и max_uses.

Пример

Агент на Agent SDK каждую ночь разбирает упавшие тесты в CI и готовит PR. Координатор раздаёт работу трём субагентам: аналитику сбоев, исправителю и ревьюеру. Поле tools не заполнили, и каждый унаследовал два десятка инструментов, включая MCP-инструменты трекера и чата. Итог: аналитик сам правит тесты, ревьюер пишет в трекер, а код агенты ищут среди задач.

Что делает архитектор:

  1. Заполняет tools по ролям: аналитику — чтение кода и логов, исправителю — чтение и правка файлов и прогон тестов, ревьюеру — только чтение кода.
  2. Заменяет универсальный загрузчик страниц на get_ci_log: он принимает номер запуска CI, а не URL, и открывает только логи своего CI.
  3. Ревьюеру почти в каждом PR нужно перепроверить пару тестов. Вместо Bash он получает узкий run_test_file: тот запускает один тестовый файл и сам проверяет путь. Весь набор тестов ревьюер запрашивает в результате, и координатор поручает прогон исправителю.

Как это спрашивают

Типичная ситуация: субагент делает чужую работу, путается в длинном списке или часто ждёт помощи другой роли. Соблазнительные неверные ходы:

  • Запрет в промпте или описании («не правь файлы», «открывай только логи CI»). Это просьба, а возможность остаётся. Верно — убрать инструмент или проверять вход в его коде.
  • Модель посильнее. И сильная модель выбирает из того, что ей дали.
  • Подробнее описать инструменты. Помогает различать похожие инструменты своей роли, но чужие из списка не уберёт.
  • Полный инструмент другой роли ради частой мелочи. Агент начнёт делать им чужую работу; нужна узкая версия.
  • Каждую мелочь — через координатора. Надёжно, но медленно.

Верный ход структурный: меняются инструменты и их границы, а не промпт или модель.

Курс vs экзамен

Экзамен считает перегрузкой уже пару десятков инструментов у одного агента. В видео урока Tool use порог для tool search — от 50 инструментов; по документации на ноябрь 2026 точность выбора падает после 30–50, а tool search советуют уже с 10. В вопросе о многоагентной системе отвечайте распределением по ролям; tool search — для агента, которому нужен большой каталог.

Документация

  • Tool search tool — точность выбора падает после 30–50 инструментов; когда включать tool search (от 10 инструментов); подгружает 3–5 нужных.
  • Define tools: Best practices for tool definitions — меньше, но более ёмких инструментов: меньше неоднозначности выбора.
  • Handle tool calls: Handling errors with is_error — инструмент выполняет ваш код; ошибка с is_error и понятной причиной помогает Claude исправиться.
  • Web fetch tool — риск утечки данных; allowed_domains, max_uses; загружает только адреса, которые уже встречались в разговоре.
  • Subagents in the SDK: Tool restrictions — поле tools: без него субагент получает все инструменты, доступные субагентам, а неуказанного инструмента в его сессии нет; лимит вложенности.
  • Create custom subagents: Let subagents spawn their own subagents — без tools субагент наследует встроенные и MCP-инструменты; tools и disallowedTools; вложенные субагенты до трёх уровней и как их запретить; Task переименован в Agent.
  • Writing effective tools for agents — with agents — фон (Anthropic Engineering): больше инструментов не значит лучше, лучше немного продуманных под важные сценарии.
