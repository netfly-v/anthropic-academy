Message Batches API

Домен 4 · подпункт 4.5

Что уже есть в курсах

  • API · Запуск оценки — в пояснении: большую оценку, результаты которой не нужны сразу, можно отправить пакетом — асинхронно и вдвое дешевле.
  • API · Параллельные рабочие процессы — в пояснении: ночную обработку без спешки отправляют пакетом; большинство пакетов готово меньше чем за час, цена на 50% ниже.

Простыми словами

Message Batches API принимает много обычных запросов к Messages API и обрабатывает их асинхронно, каждый отдельно. На ноябрь 2026 это вдвое дешевле. Большинство пакетов готово меньше чем за час, но обработка может занять до 24 часов, и срок не гарантирован.

Когда нужен пакет. Решает один вопрос: ждёт ли кто-то ответа прямо сейчас.

  • Ждёт — пользователь в чате, проверка, без которой не пройдёт выкладка. Нужен синхронный Messages API.
  • Не ждёт — ночная разметка обращений, разбор архива отзывов за квартал: это работа для пакета.

Свои инструменты внутри запроса не выполнятся. Если Claude вызывает ваш инструмент, ответ заканчивается блоком tool_use, а tool_result уходит только следующим запросом (цикл — в уроке API · Диалог с инструментами). В пакете каждый такой круг — новый пакет и до суток ожидания, поэтому агента со своими инструментами запускают синхронно.

custom_id. Результаты могут прийти в любом порядке, поэтому каждому запросу дают уникальный в пакете custom_id, например номер документа, и по нему связывают результат с запросом.

Сбои. Итог каждого запроса — succeeded, errored, canceled или expired; сбой одного не мешает остальным. Удачные ответы уже оплачены, поэтому повторяют только custom_id с неудачным итогом:

  • errored с invalid_request_error — ошибка в самом запросе, без исправления он упадёт снова. Например, документ не поместился в контекстное окно: его режут на фрагменты, у каждого свой custom_id.
  • Ошибка сервера или expired — повторяют без изменений.

Частота отправки под SLA. Считают по худшему случаю: ожидание ближайшей отправки, до 24 часов обработки, разбор и повтор упавших запросов. Правило: интервал между отправками ≤ SLA − 24 часа − запас на разбор и повтор.

Сначала выборка. Об ошибках в params API сообщает только после окончания всего пакета, а слабый промпт проявится через часы и сразу на всём оплаченном объёме. Поэтому форму запроса проверяют одним синхронным вызовом, а промпт доводят на небольшой выборке с известными ответами.

Пример

Юридический сервис извлекает поля из 20–30 тысяч договоров в сутки; поля нужны не позже чем через 36 часов после загрузки. А при загрузке юрист должен сразу видеть, не пропущены ли обязательные разделы. Что делает архитектор:

  1. Проверку разделов делает синхронным вызовом: юрист ждёт ответа.
  2. Промпт извлечения доводит на 200 договорах с проверенными вручную полями.
  3. Извлечение отправляет пакетами раз в 8 часов: 36 − 24 − 4 часа запаса на разбор и повтор. Повторы — синхронные: новый пакет мог бы снова занять сутки.
  4. custom_id — номер договора.
  5. Из 25 000 запросов 140 завершились с errored. Сто длинных договоров не поместились в окно — их режут по разделам (contract-58213-p1, contract-58213-p2) и отправляют заново. Сорок с ошибкой сервера повторяют как есть.

Как это спрашивают

В вопросе обычно смешаны блокирующие и фоновые вызовы, иногда есть срок готовности или упавшие запросы. Соблазнительные неверные ходы:

  • «Пакеты обычно готовы за час — подойдут и блокирующему шагу». Срок не гарантирован, считают по худшему случаю.
  • Перевести на пакеты агента со своими инструментами. Каждый круг tool_use → tool_result стал бы новым пакетом.
  • Переотправить весь пакет или повторить упавшее без изменений. Первое — повторная плата за готовое, второе не поможет, если ошибка в самом запросе. Верно — повторить только неудачные custom_id, исправив ошибочные.
  • Сразу запустить весь объём и чинить по ходу. Каждая итерация — целый пакет и до суток ожидания. Верно — сначала довести промпт на выборке.

Курс vs экзамен

На экзамене: многоходового вызова инструментов внутри запроса пакета нет, и если модель вызывает ваши инструменты, пакет не подходит. По документации на ноябрь 2026 это верно для клиентских инструментов; серверные (web search, code execution и другие) проходят в пакете тот же цикл, что и в синхронном API. А «Tool use» и «Multi-turn conversations» в списке возможностей пакетов значат лишь, что в запрос можно передать инструменты и готовую историю диалога.

Документация

  • Batch processing — скидка 50%, до 24 часов на пакет (большинство — меньше часа), четыре итога запроса, порядок результатов и custom_id, какие ошибки исправлять перед повтором, серверные инструменты в пакете, проверка формы запроса через Messages API.
  • Create a Message Batch — поле custom_id: зачем нужно, уникальность, допустимые символы и длина.
  • Tool use with Claude — клиентские инструменты выполняет ваш код: ответ с stop_reason: "tool_use", результат — в следующем запросе; серверные выполняет Anthropic.
  • Context windows: Context window overflow behavior — вход больше окна даёт 400 invalid_request_error («prompt is too long»).
  • Define success criteria and build evaluations — цикл: тестовые случаи, черновой промпт, итерации и доработка, финальная проверка, выпуск.
